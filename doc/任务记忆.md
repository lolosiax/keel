## 1. 项目定位

- **Keel**：Kotlin/Native 的模块化 Web 框架，心智模型是 Tomcat/WAR + Bukkit/Spigot。
- Host 是容器；插件是部署单元；目标平台 `mingwX64`、`linuxArm64`（RK3566）、`linuxX64`。
- 硬约束来自 [前序讨论.md](前序讨论.md)：
  - K/N 运行时不可安全卸载；
  - Host 与插件是两个运行时，只能传 blittable / 句柄 / 事件；
  - 协程与调度器不跨 C ABI；
  - 热路径用 CBOR/Protobuf，不用 JSON。
- 目录角色、依赖方向与构建 / 发布约定见 [../AGENTS.md](../AGENTS.md) §0–§7。

## 5. 已确认的设计决策

1. **Classpath 只做资源**，不是类加载；K/N 不能跨插件加载类。
2. 插件包是 `.keel`（zip）：根 `plugin.json`、`lib/<target>`、`resources/`。
3. 资源**不解包**；插件与 Host 都按 zip 随机读。
4. 插件读自己：本地 `.keel`；缺失回落 Host；跨插件只能 `ctx.classpath.of(id)`。
5. `.keel` 真实路径只在 Host；插件侧只拿 `ClasspathRef`，`origin` 为 `keel://<id>`。
6. 卸载以 Host 注册表为准：generation 失效，旧引用读取抛 `ClasspathNotFoundException`。
7. 普通 exe/dll/so 走原 `classpath.zip` 嵌入；插件 dylib 不嵌 `classpath.zip`。
8. `keel-classpath` 独立可用；`keel-api` 只依赖它的类型；`-full` 负责 Host 注册表与代理。
9. `ClasspathTransport` 接口与 Host 侧实现已落地；插件侧（经事件泵 / C ABI）的远程实现尚未接。
10. **Host 的 Ktor 与事件泵是两个执行者，不需要合并**：Ktor handler 用
    `suspendCancellableCoroutine` 把请求投给事件泵并挂起，泵线程收到 COMPLETE 后按
    correlation resume；`ApplicationCall` / `Continuation` 只留在 Host 运行时，绝不跨 ABI。
    实现是 `Channel<HostRequest>` + `CompletableDeferred`：pending 表只由泵线程读写，
    外部线程不碰它。
11. **单 exe = 预编译 launcher + 注入的 bundle**：用户工程始终保持插件工程形态，
    不声明 application / executable；bundle 用 PE 资源（Windows）或文件尾 trailer（Linux）携带，
    运行期只在内存打开，同 id 以磁盘 `plugins/` 优先。

### 6.0.1 contract-first `@PublicApi` 设计（2026-11-21）

- 新稿：[contract-first-public-api.md](contract-first-public-api.md)。
- **已落地：Context 组件化切片（不含 KSP contract-first）**：
  - `keel-api` 的 `Context` 核心只剩 `components()` / `component(id)` / `addComponent()` / `removeComponent()` / `destroy()`；
  - remove 只解除挂载并返回实例；add/remove 自动维护 `component.context`；
    `Context.destroy()` 先解绑、再按挂载逆序级联释放组件，持有方用 try/finally 保证执行；
    挂载期间第三方调用 `component.destroy()` 无效果；`WebRequestComponent` 由独立实现类挂进组件表；
  - `LocalContext` 放 `plugin` / `local` / `server` / `config`，不进 api 工件；
  - 契约里的本地状态用 `@LocalMember` 显式标注（`Component.context`）：KSP 不生成跨界分发，
    生成的代理在本地用 `null` 初始化；`keel-plugin-ksp` 同时补了重复 typeId 检查；
  - Web 能力拆成 `WebRequestComponent` + `WebContext`；
  - 业务语法糖在 `ContextExt.kt`（`ctx.request()` / `ctx.userId()` / `ctx.query(...)` / `ctx.hasPermission(...)`，均 suspend）；
  - `RequestContextImpl` 实现 `LocalContext` / `WebContext`，`WebRequestComponentImpl` 挂进组件表；
  - router KSP 生成的代码改用 `ctx.request()` / `ctx.pathParameters()`，并支持控制器参数声明 `Context` 子接口。
- **已落地（2026-11-21）**：`keel.api.mode`（默认 `MIRROR`）+ core / `CONTRACT_FIRST` 生成；
  `keel-api` 已接 KSP，生成 `ContextKey` / `ContextProxy` / `WebContextProxy` /
  `WebRequestComponentProxy` / `ComponentProxy`（V1 提交制，落在 `src/commonMain/kotlin`）；
  wire 支持可空共享对象、共享对象列表与接口继承展开；`@PublicApiProvider(vararg contracts)` 注解已添加。
- **已落地（续）**：`@PublicApiProvider` 的发现与注册——plugin 模式生成多契约并集分发器并写进
  `KeelPluginPublicApi.setup`；core 模式（`keel.provider.dir`）为 `RequestContextImpl` 生成
  `RequestContextImplDispatcher` 与 `RequestContextImplProvider.register(directory, impl)`。
- **已落地（续）**：共享对象释放语义——`PublicApiDirectory.release(instance)` +
  `HostSubjects.PUBLIC_API_RELEASE` + `HostShared.release`（Host 删除 entry / 单例映射，
  后续调用得到 “shared object closed”）；`LocalContext.shareHandle()` 按需登记
  `RequestContextImplProvider`，`RequestContextImpl.destroy()` 在 finally 里释放句柄。
- **已落地（续）**：挂载组件的跨界登记——`WebRequestComponentImpl` 标
  `@PublicApiProvider(WebRequestComponent::class, Component::class)`，core 模式生成
  `WebRequestComponentImplDispatcher` / `...Provider`；`shareHandle()` 首次登记时同时登记已挂载组件，
  `addComponent` 在已共享时补登记，`removeComponent` / `destroy` 释放。
  未提供 provider 的自定义组件不导出：`PublicApiDirectory.handleOfOrNull` 让 `components()` /
  `component()` 在跨插件视图里略过它，而不是整次调用失败。
- **已落地（续）**：跨界登记内化——`SharedExport.sharedRef(directory)` 由
  `PublicApiObjects.handleOf` 自动调用；把 `Context` 作为参数传给别的插件时，
  生成的代理编码参数即完成登记，业务代码不需要 `shareHandle()`，也不手工构造代理。
  `LocalContext.shareHandle()` 只保留给需要句柄本身的高级场景。
- **端到端冒烟（2026-11-21）**：`keel-plugin-hello` 新增
  `GET /api/hello/context`（普通业务写法，直接 `ctx.components()`）与
  `GET /api/hello/context-bridge`（自检：用 `handleOf(ctx)` 模拟另一个插件拿到的代理）。
  bridge 返回 `handle=3 components=keel.web.request path=/api/hello/context-bridge`，
  日志按 4 → 3 逆序释放句柄。
  复现：`$env:KEEL_AUTH_WHITELIST_EXACT="/api/hello/context,/api/hello/context-bridge"; gradlew -p keel-plugin-hello keelRun "-Pkeel.run.serveMs=30000"`。
- 下一步：真正的双插件 Context 传递示例（插件 A 把 Context 交给插件 B），
  以及自定义 `Component` 的通用 provider 登记约定（当前只支持 keel-api 自带的 Web 组件）。
- 关键决策：
  - `MIRROR` 始终是默认模式；只有手写 API 的插件才切 `CONTRACT_FIRST`；
  - `keel-api` 始终是 `CONTRACT_FIRST`；同一构建不允许混用；坐标不变；
  - api 模块只两种形态：MIRROR 生成的 api（不可手改）或 CONTRACT_FIRST 的手写 api。
- Unity 风格 `Context.getComponent<T>()` 本版本不做：契约只有 `component(id)`，
  业务用声明方的 typed 方法（`WebContext.webRequest()`）与 `Context` 扩展。
- 阶段 0 / 阶段 1 的生成侧与 provider 注册已完成；单插件内的「共享 → 跨界调用 → 释放」
  已端到端跑通，剩余是双插件互传示例与自定义组件的 provider 约定。

   - 供 C 侧对象句柄（能力对象等）使用；`@PublicApi` 走的是 Host 逻辑句柄（整数 id + 表），不依赖它。

3. **业务载荷格式**（大部分已完成）
   - 跨模块服务、Host 反向请求与存储统一用 CBOR 信封（`ServiceWire` + 各 DTO）；
   - 句柄列表与两阶段批量序列化仍未做。

4. **插件侧 `ClasspathTransport`**
   - Host 侧 `HostClasspathTransport` 已通；插件侧要经事件泵向 Host 注册表取资源；
   - `PluginContext.classpath` 目前是 `EmptyClasspath`，`RemoteClasspath` / `remotePluginClasspath`
     没接运行时。

5. **插件 id 与元信息**
   - Host 侧 `KeelPackageManifest.toMetadata()` 已能给出 id / name / version / entry /
     authors / color；但插件运行时仍只有 `plugin_id`（`PluginMetadata.name` / `version` /
     `entry` 是空串），需要把 manifest 元信息下发到 Worker。

6. **Linux 导出验证**
   - `.def` 只在 mingw 生成；linux 上 `@CName` 符号是否进 `.dynsym`（默认 visibility）未实测，
     需要在板子上跑一次 `dlopen` + `dlsym`，不行就加 version-script / `--dynamic-list`。

7. **SQLite / MariaDB 与 ORM（按 database-orm-plan 推进）**
   - SQLite 已完成：`keel-thirdparty` 的 `sqlite` 条目 + `keel-database-sqlite` 能力包，
     exec / query / 参数 / 事务 / NULL / BLOB / Unicode 冒烟通过（ABI v1）；
   - `Context.database` / `transaction` / `execute` / `query(sql)` 扩展与 `requireDatabase()` 已加；
   - `keel-orm` 运行时 + `keel-orm-ksp` 生成器 + `moe.lolosia.keel.database` Gradle 接线已落地，
     D1 单表能力（查询 / CRUD / 分页 / 事务 / 方言渲染）在 hello 的 `HellUser` 切片上跑通；
     ORM 生成物写进 `build/generated/keel/orm` 并由插件挂进 `nativeMain`（不提交、不污染 src），
     Worker 入口自动 `OrmMetaBootstrap.install()`；
   - MariaDB 后补：`keel-database-mariadb` 目前只响应 `select 1`，其余语句返回 `KEEL_ERR_UNSUPPORTED`；
   - `basic-biz` 本次不迁 SQLite，仍跑 MariaDB；多库兼容后置；
   - 未做：ABI v2（options / last_insert_id / DECIMAL·TIMESTAMP·JSON·UUID）、
     关联 / `Children<T>` / `withChildren` / `saveGraph` / 实体序列化（D2）；
   - 生成代码不再进 git：ORM 已改成 `build/generated/keel/orm` + Gradle 挂载；
     api 生成的 V1 提交制是过渡，后续按同样方式切到 `build/generated/keel/api`
     （见 [public-api-design.md](public-api-design.md) §4.2）；
   - 详见 [database-orm-plan.md](database-orm-plan.md)。

8. **M2 业务插件**
   - 已完成：rbac 默认实现 `keel-plugin-basic-rbac`（表结构、组 / 组继承 / 组规则 / 用户直授、
     内置组默认规则、`Authorizer`、管理路由）与 `keel-plugin-basic-biz`；
   - 契约以 `keel-plugin-rbac-api` / `keel-plugin-basic-biz-api` 发布，第三方 rbac 实现可原位替换；
   - 仍阻塞在真实 `libmariadb` 接入；SQLite 先做 conformance，不迁移 basic-biz。

### 6.5 发布链 / basic-biz / 独立插件仓库 / keelRun（2026-11-09 续）

- **发布链**：新增 `gradle/publishing.gradle.kts`；`keel-api` / `classpath*` / `database-api` /
  `*-api` / `keel-host` / `keel-database-mariadb` 都能 `publishToMavenLocal`。
  `keel-abi` 发布 zip；`keel-abi-gradle-plugin` 在独立构建里按
  `moe.lolosia.keel:keel-abi:<version>@zip` 解析，不再依赖兄弟目录。
  根构建新增 `publishAll` / `publishAllToMavenLocal`。
- **cinterop 元数据坑**：KMP 的 `nativeMain` 元数据编译会把 commonized cinterop 结构体降级成
  不透明类型；`KeelDatabase` / `QueryResult` 的字段访问改成 `nativeMain` expect +
  `src/nativeCinteropMain` 共享 actual。
- **basic-biz**：见 §3.16；`requires: ["database"]`，DB 不可达时只告警、不阻断启用。
- **Host HTTP 补齐**：响应头、HEAD `Content-Length`、通配路由 `{...}`、非 GET/HEAD 按字节读体。
  请求体仍整包缓冲，大文件 PUT 会占内存。
- **独立仓库 `lolosia-keel-plugins`**（本机 `E:\Dev\Kotlin\lolosia-keel-plugins`，工作区 junction）：
  `lolosia-webdav`（WebDAV 12 方法、Range、LOCK/UNLOCK）与 `lolosia-dashboard`（`/proc` 指标曲线）。
  依赖 `moe.lolosia.keel:*:<keelVersion>`；`mavenLocal()` → `keel.repo`。
- **keelRun**：`moe.lolosia.keel.plugin` 新增任务，解析
  `keel-host-dev-<target>:<keelVersion>@zip`，按 `plugin.json.requires` 自动加
  `keel-database-mariadb` 等能力包，组装 `build/keel-run/{host,plugins}` 后启动 Host。
  `-Pkeel.run.host/port/serveMs` 可覆盖。已实测 OPTIONS/GET/PUT/PROPFIND。
- **构建 / 运行分离**：`keelRun` 拆成 `keelPrepareHost`（解 Host）+
  `keelPrepareRun`（打包 `.keel`、拷贝配置 / 数据）+ `keelRun`（只 exec）。
  `keelRun` 默认注入 `FORCE_COLOR=1`，修复 Gradle exec 把 stdout 接到管道后
  Host 的 ANSI 探测关闭、控制台无颜色的问题。
- **IDEA 插件 `keel-idea-plugin/`**：IntelliJ Platform Gradle Plugin 2.20.0，
  目标社区版 2025.2.6。静态扫描 `plugin.json` + `build.gradle.kts` 识别插件工程；
  启动后自动创建运行配置；`keelPrepareRun` 作为 Gradle before-run task 在 IDEA 的
  Build 面板执行（保留 Gradle 进度 / 计时 / 错误统计），构建完成后 Run 面板只启动
  Host 并显示 Host 日志。默认不参与 `buildAll`。已知限制：Kotlin/Native 断点仍需
  CLion / IDEA Ultimate。
- **已知阻塞**：release Host 在插件 HTTP 响应路径 `ACCESS_VIOLATION`，debug Host 正常；
  `keelRun` 暂时固定解析 debug 包。生产 release 前必须定位。
