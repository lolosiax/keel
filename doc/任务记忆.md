## 1. 项目定位

- **Keel**：Kotlin/Native 的模块化 Web 框架，心智模型是 Tomcat/WAR + Bukkit/Spigot。
- Host 是容器；插件是部署单元；目标平台 `mingwX64`、`linuxArm64`（RK3566）、`linuxX64`。
- 硬约束来自 [前序讨论.md](前序讨论.md)：
  - K/N 运行时不可安全卸载；
  - Host 与插件是两个运行时，只能传 blittable / 句柄 / 事件；
  - 协程与调度器不跨 C ABI；
  - 热路径用 CBOR/Protobuf，不用 JSON。

### 2.1 本机 Gradle 注意事项

- 机器代理 `localhost:33210` 经常没在监听；所有命令加：
  ```powershell
  "-Dhttp.proxyHost=" "-Dhttps.proxyHost="
  ```
  ⚠️ PowerShell 会把不带引号的 `-Dhttp.proxyHost=` 拆成两个参数，报
  `Task '.proxyHost=' not found`，必须加引号。
- includeBuild 多、K/N 链接重时可能 `Metaspace`；先 `gradlew --stop`，
  再加 `-Dorg.gradle.jvmargs=-Xmx4g`。
- 尚未发布 release 包：`keel` 版本与 `KEEL_ABI_VERSION` 仍可自由调整；正式发布后再改 ABI 必须升版本。

### 3.7 `keel-abi`（C 实现 + 静态库）

全新顶层构建，`src/nativeCpp/` 里放 ABI 的实现，`keel_abi.h` 也在这里（唯一布局来源）。

| 文件 | 作用 |
| --- | --- |
| `keel_abi.h` | 事件 / 状态码 / 函数表 / 导出入口；`KEEL_EXPORT` 只给 bootstrap、shutdown |
| `keel_queue.c` | 定长环形缓冲，节点一次性预分配，push/pop 带超时 |
| `keel_event.c` | `keel_event_release_default`（按发送方 CRT free） |
| `keel_plugin.c` | `bootstrap`（纯 C，起泵线程）/ 泵循环 / START 握手 / `shutdown` |
| `keel_platform.h` | mingw 用 `CRITICAL_SECTION` + `CONDITION_VARIABLE` + `CreateThread`；linux 用 pthread |

任务：`keelAbiObjects<target>` → `keelAbiArchive<target>` → `keelAbiPackage`，
产物 `libkeel_abi.a` + `include/keel_abi.h` 打进 `keel-abi-<version>.zip`。
默认只编主机目标（K/N 下载的 linux gcc 是 Linux 可执行文件），
跨目标用 `-Pkeel.abi.targets=linuxX64`。

`moe.lolosia.keel.abi`（`keel-abi-gradle-plugin`）负责解包 + `linkerOpts("-L…", "-lkeel_abi")`：
Host 在 `build.gradle.kts` 显式 `id("moe.lolosia.keel.abi")`，
插件工程由 `moe.lolosia.keel.plugin` 自动 apply。
`keel-plugin-gradle-plugin` 因此依赖 `keel-abi-gradle-plugin`——
`pluginManager.apply(id)` 只查 buildscript classpath，不查 `pluginManagement.includeBuild`；
这个依赖靠 `keel-plugin-gradle-plugin/settings.gradle.kts` 里的
`pluginManagement.includeBuild("../keel-abi-gradle-plugin")` 在 composite 下替换成本地工程。

sharedLib 额外做两件事（Kotlin 侧不做任何标注）：

- `-u keel_plugin_bootstrap`：Kotlin 代码从不引用静态库成员，不强制拉入就没有泵线程；
- 生成 `build/generated/keel-abi/<target>-def/keel-plugin.def` 并作为链接输入：
  Kotlin 的 `@CName` 符号**不会**自动进 PE 导出表，Host 会 `dlsym` 不到。
  默认导出 `keel_plugin_bootstrap` / `keel_plugin_shutdown` / `keel_plugin_worker_main`，
  用别的入口名时 `keelAbi { export("...") }` 追加。

`KeelQueueTag` 在头文件里用 `KEEL_CINTEROP` 分成两支：cinterop 侧看到只有 `void *reserved` 的
**完整占位结构体**（宏由 `keelabi.def` 的 `compilerOpts` 注入），C 实现侧仍只看到前向声明。
这样 cinterop 把类型生成到 `moe.lolosia.keel.abi.c`，而不是 IDE 中间源集索引不到的
`cnames.structs`。Kotlin 侧只能持有指针，不能解引用、分配、按值传递或 `sizeof`。

日志事件：`KEEL_EVENT_LOG` + `KeelLogLevel`（TRACE / DEBUG / INFO / WARN / ERROR / FATAL）。
插件用 `keel_payload_alloc` / `keel_payload_copy` 写 UTF-8 载荷，并挂上本二进制的
`keel_event_release_default`；Host 在 `popHostEvent` 里复制载荷后再 release。

健康检查：`KEEL_SUBJECT_PING` 是最小请求 / 应答回路——Host 向插件投
`COMMAND{subject=PING, correlation=N}`，插件回 `COMPLETE{correlation=N, status=OK}`。
Host 在每个插件启动完成后体检一次（`ping <id> ok`），这是目前唯一在运行期跑通的往返路径。

调度器定时：`keel_plugin_set_wakeup(delayMs)` 设置泵线程下一次 pop 的超时；到点且 inbox 为空时，
C 侧投一条 `COMMAND{subject=KEEL_SUBJECT_TIMER}` 给插件分发表，由 `WorkerScheduler.tick()`
在同一个 Worker 线程上跑到期任务并重新定时。delay < 0 表示取消定时。

### 3.8 Host 插件加载器（Kotlin 部分）

`keel-host` 的 `host/plugin/`：

| 文件 | 作用 |
| --- | --- |
| `PluginLoader.kt` | 扫描目录、校验 manifest、解出动态库、注册 classpath；`loadAll` 把失败隔离成 `PluginLoadFailure` |
| `LoadedPlugin.kt` | 已可 `dlopen` 的插件：manifest + 缓存里的库路径 + `ClasspathRef` |
| `PluginLoadFailure.kt` / `PluginLoadResult.kt` | 单条失败原因 / 一轮扫描结果 |
| `NativeLibrary.kt` + `.mingw.kt` / `.linux.kt` | `LoadLibraryA`/`GetProcAddress` 与 `dlopen`/`dlsym`；不提供 close（K/N 运行时不可卸载） |
| `HostAbi.kt` | 进程内收件箱 `keel_queue_create` + `KeelHostApi` 表；`popHostEvent` 复制标量与载荷后归还 |
| `LogEvent.kt` / `HostPump.kt` / `PluginNames.kt` | 日志事件解码、收件箱 drain（按 `target` 转发）、`plugin_id` → manifest id |
| `PluginRuntime.kt` | `startPlugin`：bootstrap → 投 START → 等 COMPLETE；`shutdown()` 调 `keel_plugin_shutdown` |
| `PluginFs.kt` | 最小文件读写（查大小、覆盖写） |
| `HostTarget.kt` | 运行期目标名 `mingwX64` / `linuxArm64` / `linuxX64`，用于选 `lib` 条目 |
| `package.native.kt` | `listNames`，mingw 与 linux 共用 posix `opendir` |
| `package.mingw.kt` / `package.linux.kt` | `mkdirs`：mingw 的 `mkdir` 只有一个参数，linux 是 path + mode |

CLI：`keel-host --plugins <目录> [缓存目录] [--serve | --serve-ms=<n>]`，
缓存默认 `<目录>/.cache`，库落到 `<cache>/<id>/<version>/<文件名>`；
**同名同大小不重写**（避免覆盖已映射的库）。
加载成功后会逐个启动并 ping 体检；默认清空收件箱后退出，带 `--serve` 时主线程进入事件循环
（`--serve` 一直服务到进程被杀，`--serve-ms=<n>` 服务 n 毫秒）。
进程退出前逐个 `shutdown()`；单个插件启动失败只打印原因，不影响其它插件。

日志：Host `Log` 统一格式 `HH:mm:ss 级别 模块 来源 : 消息`；
模块列默认 15（Host / 插件名 / 自定义 tag），来源列默认 40（`短类名:行号`）。
启动时打印版本、可执行文件、pwd、OS/架构、target、ABI；loader 只打印
`<keel>!/<包内库路径>`、插件名、版本与作者，不再打印实际 cache 路径。

校验顺序（`PluginLoader.load`）：manifest 可读 → `id` 非空 → `abiVersion == 1` → `entry` 非空
→ `id` 不重复 → 当前目标有 `lib` 条目 → 包内确实有该库。
`sha256` 只被读进 `PluginClasspathEntry`，尚未校验。

联调必须知道的运行时事实：

- `plugin_id` 由 Host 从 1 开始按加载顺序自增，**只在当前进程内有效**，重启后重排，
  也不写进 manifest；`PluginNames` 用它把日志里的 id 映射回插件名。
- 单个插件启动超时 5000ms；等待某插件 `COMPLETE` 期间，其它插件的非 `KEEL_EVENT_LOG`
  事件会被直接丢弃。
- Host 收件箱容量 256 条；插件侧 inbox 同样是 256（`keel_plugin.c` 的 `KEEL_INBOX_CAPACITY`）。
- `KeelHostApi.handle_new/retain/release` 全部为 `null`，插件无法申请跨运行时句柄。
- 插件侧 `PluginMetadata` 只有 `id` 有值（`plugin_id.toString()`），`name` / `version` / `entry` 是空串。
- `KeelHostApi.host_inbox` 是**普通指针字段**，不是函数指针：插件在自己的 Worker 线程上读取它
  不会进入 Host 运行时。早先的函数指针写法会让插件线程调用 Host Kotlin，违反线程模型，已修。
- 转发按 `target` 字段走：`target == 0` 表示 Host，其它值必须在 `pluginInboxes` 里查得到，
  否则事件告警一次后丢弃；转发成功后载荷所有权交给目标插件，Host 不再 release。

### 3.9 日志调用点（keel-logger）

`keel-api` 新增 `Log` 门面与 `LogSite` / `LogSiteKind` / `LogSink` / `LogSiteCodec`。
`moe.lolosia.keel.logger`（Gradle 插件 + 编译器插件）在 IR 阶段把
`Log.info(xxx)` 改写成 `Log.of(displayName, file, line, packageName, className, functionName, kind).info(xxx)`。

- `displayName`：类内为完整类名；类外为 `包名.文件名首字母大写 + Kt`。
- `file`：相对 Gradle 调用目录的路径；Gradle 插件传 `workspaceRoot` + `sourceRoot`，
  编译器插件按 `包名/文件名` 反查（IR 只暴露文件名）。
- Host `HostLogSink`：时间只保留 `HH:mm:ss`；模块列默认 15（`Log.moduleWidth`），
  来源列 `短类名:行号` 默认 40（`Log.displayNameWidth`）。
- 来源列压缩：保留类名，包段先各 1 字，再从右往左逐级加长直到用满预算；
  仍放不下才从左丢段并加 `…`（例：`moe.lolo.keel.plugi.hello.HelloPlugin:18`）。
- 颜色：Host 启动时探测 stdout（Win32 `GetConsoleMode` + VT、Linux `isatty` + `TERM`）；
  配色（整段时间默认色；TRACE 亮灰、DEBUG 浅蓝、INFO 绿、WARN 黄、ERROR 红、
  FATAL 红底黑字；来源类名 cyan、`:行号` faint），模块名用 FNV-1a 哈希取 12 色盘
  （普通 6 色 + 亮色 6 色）。
  `plugin.json` 的 `color`（`#RRGGBB` / `#RGB`）优先于哈希色，走 ANSI truecolor
  （`38;2;r;g;b`）；颜色非法时回落到哈希并打一条 Loader 警告。
  支持 `NO_COLOR` / `CLICOLOR=0` 关闭与 `FORCE_COLOR` 强制开启。
- 模块名：Host 日志默认 `Host`，插件日志默认用 manifest `name`（空则 id），
  显式 `tag = "Loader"` / `tag = "EventBus"` 可自定义。
- 插件 `NativePluginLogger`：有 `LogSite` 时用 `LogSiteCodec` 编码模块名与来源进
  `KEEL_EVENT_LOG`，Host 解析后按模块 + 插件侧类名展示；`ctx.logger` 仍是纯文本。
- 自动接线：`moe.lolosia.keel.plugin` 自动 apply logger；`keel-host` / `keel-launcher`
  显式 `id("moe.lolosia.keel.logger")`。`keel-api` 自身不挂（库不依赖构建期插件），
  因此 `PluginWorker` 里的兜底错误日志没有调用点。

### 3.10 运行时行为边界（当前实现只到哪）

这些是代码里真实行为、但接口看不出来的地方，接新功能前必须知道：

- 插件侧 `PluginWorker.dispatch` 处理两种事件：`SHUTDOWN` 与 `COMMAND{subject=PING}`（回 COMPLETE）；
  BUS / CANCEL / DISPOSE 与未知 subject 会打一条告警（每种 kind 一次）后被丢弃。
- Host 侧 `HostPump.drain` 按 kind 分派：`KEEL_EVENT_LOG` 就地消费；`target != 0` 的事件
  转发到目标插件 inbox；`target == 0` 的其它事件、或目标不在线的事件，告警一次后丢弃。
- `HostPump.requestPlugin` 是 Host 发起的同步请求：投 COMMAND 后阻塞等待同 correlation 的
  COMPLETE（默认 2000ms），等待期间仍会消费日志；目前只有 PING 用它。
- 插件侧还不能主动发起请求：没有「取目标 id / 构造事件」的 API；调度器已能提供
  启动后的触发点，下一步补发送 API 即可跑插件间消息。
- 调度器任务只在 Worker 线程执行：泵线程按最近截止时间超时唤醒并投 `KEEL_SUBJECT_TIMER`；
  C 侧用 `keel_now_ms()` 计时，Kotlin 侧用 `TimeSource.Monotonic` 记截止时间，两者只传相对毫秒。
- `schedule` / `cancel` 只能在 Worker 线程调用；取消不会提前唤醒（最多空跑一次），
  周期任务落后超过一个周期时跳过积压，不补跑。任务抛异常只记日志，不中断泵线程。
- 插件日志在收件箱满时静默丢弃：`NativePluginLogger` 会归还载荷，但不报错、不打点。
- `PluginWorker.plugin` 是单例，没有重入保护：重复 START 会覆盖实例，且不调用旧实例的 `onDisable`。
- 卸载只让资源引用失效（`HostClasspath.unregister`），不 `dlclose`；`PluginLoader.unload` 目前没有调用点。
- 默认模式只在「全部插件启动完」和「全部 shutdown 后」各 `drain` 一次；
  `--serve` 时主线程进入 `HostPump.serve()` 循环（单线程、200ms 超时），
  这是目前唯一的长驻事件循环。`--serve`（不限时）只能靠杀进程结束，不会走优雅 shutdown。

## 5. 已确认的设计决策

1. **Classpath 只做资源**，不是类加载；K/N 不能跨插件加载类。
2. 插件包是 `.keel`（zip）：根 `plugin.json`、`lib/<target>`、`resources/`。
3. 资源**不解包**；插件与 Host 都按 zip 随机读。
4. 插件读自己：本地 `.keel`；缺失回落 Host；跨插件只能 `ctx.classpath.of(id)`。
5. `.keel` 真实路径只在 Host；插件侧只拿 `ClasspathRef`，`origin` 为 `keel://<id>`。
6. 卸载以 Host 注册表为准：generation 失效，旧引用读取抛 `ClasspathNotFoundException`。
7. 普通 exe/dll/so 走原 `classpath.zip` 嵌入；插件 dylib 不嵌 `classpath.zip`。
8. `keel-classpath` 独立可用；`keel-api` 只依赖它的类型；`-full` 负责 Host 注册表与代理。
9. `ClasspathTransport` 接口与 Host 侧实现已落地；插件侧（经事件泵 / C ABI）的远程实现尚未接。

## 6. 已知缺口 / 下一步

加载、握手与 C ABI 的主链路已打通（§3.7 / §3.8）；剩下的按依赖顺序如下。

### 6.1 主线待办

1. **事件分发与路由（Host→插件→Host 已闭环）**
   - 已做：Host 按 `target` 转发到插件 inbox（`registerPluginInbox` + `popHostEventRaw`）；
     两端未处理事件各告警一次；`host_inbox` 改成普通指针，消除插件线程调用 Host Kotlin；

     调度器（§4.5）已提供启动后的触发点，补上发送 API 就能跑插件间消息。

3. **业务载荷格式**
   - 除 `KEEL_EVENT_LOG`（UTF-8 + `LogSiteCodec`）外没有任何业务编码；
   - 需要定 CBOR / Protobuf 信封（channel、版本、句柄列表），再做两阶段批量序列化。

4. **插件侧 `ClasspathTransport`**
   - Host 侧 `HostClasspathTransport` 已通；插件侧要经事件泵向 Host 注册表取资源；
   - `PluginContext.classpath` 目前是 `EmptyClasspath`，`RemoteClasspath` / `remotePluginClasspath`
     没接运行时。

5. **插件 id 与元信息**

## 7. 易踩的坑

- 编译器插件与 Kotlin 版本强绑定：`keel-logger-compiler-plugin` 的
  `compileOnly(kotlin-compiler-embeddable)` 必须与 `libs.versions.kotlin` 完全一致；
  升级 Kotlin 要同步升它并重跑 host / hello 的日志验证。
- 单独构建 `keel-host` / `keel-plugin-hello` 时，除 `keel-logger-gradle-plugin`
  走 `pluginManagement.includeBuild` 外，编译器插件 jar 还要
  `--include-build=../keel-logger-compiler-plugin`，否则解析不到
  `moe.lolosia.keel.toolchain:keel-logger-compiler-plugin`。
- IR 的 `arguments` 列表按“全部形参”排布（含 dispatch / extension receiver），
  写实参要按 offset 加 1；`IrGetEnumValueImpl` 是编译器 internal API，所以
  编译器插件调用 `Log.of` 的 `Int` 重载传 `kind.ordinal`。
- `-Xplugin` / `-P` 由 `KotlinCompilerPluginSupportPlugin` 自动挂载，不要手写
  `freeCompilerArgs`，否则插件 jar 不进 `@Classpath`、改了插件不重编。
- 实测改完编译器插件后，消费方 native 编译任务不一定重新执行；联调时先
  `gradlew -p <消费方> clean` 再编译，避免拿旧 IR 验证。
- `keel-classpath-full` / `keel-api` 现在依赖 `keel-classpath`；单独 `-p` 构建必须带
  `--include-build=../keel-classpath`，否则去 Maven 找不到。
- `keel-plugin-hello` 自动依赖 `keel-classpath-full`；单独构建必须带
  `--include-build=../keel-classpath-full`。
- K/N 2.4 里 `kotlinx.cinterop.toWideString` 已不存在；要调 Windows 的 `W` API 得自己
  `allocArray<WCHARVar>` 拼 UTF-16。实测 mingw 的 `platform.posix` 有 `opendir` / `readdir`，
  但 `mkdir` 只有 path 一个参数（linux 是 path + mode），两端签名不同，必须 expect/actual。
- Kotlin 的 `@CName` 符号不会自动进 PE 导出表：不生成 `.def` 的话 dll 里只有 C 那些
  `__declspec(dllexport)` 符号，Host `dlsym(entry)` 直接拿到 null。
- 改了 `keel-abi/src/nativeCpp/*.c` 之后要确认 **归档任务重跑**：`keelAbiArchive<target>`
  以前没声明 inputs，只重编 `.o`、`.a` 还是旧的（症状：Kotlin 按新签名调用、C 还是旧签名，
  进程直接 access violation）。现在归档有 `inputs.dir`，链接任务也把库目录挂成输入。
- 插件库缓存按「同名 + 同大小」判断是否重写：换了同尺寸的库会继续用旧文件，
  联调 ABI 时先删 `<cache>/<id>/<version>/` 再跑。
- KSP 处理器依赖必须在 `ksp<target>` 配置**创建的那一刻**加进去：KSP 在自己的
  `afterEvaluate` 里创建配置并固定处理器 classpath，晚于它的 `afterEvaluate` 再加就只有
  空 classpath（症状：`kspKotlinMingwX64` 跑完但什么都没生成，链接报
  `undefined symbol: keel_plugin_worker_main`）。所以 `moe.lolosia.keel.plugin` 用
  `configurations.configureEach` 挂 `keel-plugin-ksp`。
- KSP2 没有 KSP1 的回退：`ksp.useKSP2=false` 会直接报 "KSP1 is no longer available"。
- **IDEA 同步会编译中间源集的 metadata**（`compileNativeMainKotlinMetadata` 等），
  这些任务在 `-p <项目> linkDebug…` 里不会跑，所以本地能过、同步报错很常见：
  - `expect class` 继承接口时，必须在 expect 里显式声明 `override fun close()`
    （metadata 看不到各目标 actual）；actual 侧要写 `actual override fun close()`。
  - `nativeMain` 里直接用 `fseek` / `ftell` 会被 commonize 拒绝：mingw 的 `long` 是 32 位、
    linux 是 64 位，签名不一致。这类调用要拆成 `expect` / `actual`（见 `fileSizeOrNull`）。
  - 用到 keel-api 的 cinterop 声明的中间源集，需要在自己的 `gradle.properties` 里
    打开 `kotlin.mpp.enableCInteropCommonization=true`（根目录的不会下发）。
- `keel-host` 的 `settings.gradle.kts` 通过 `pluginManagement.includeBuild` 引入
  `../keel-classpath-gradle-plugin`；`keel-plugin-hello` 引入 `../keel-plugin-gradle-plugin`。
  改插件后要重新构建插件，Gradle 会自动处理。
- 构建期工具各自带一份发布仓库配置；`local.properties` 始终按 `../local.properties` 找，
  单独 clone 某个构建时它必须与仓库根同级。
- `keel-launcher` 调用 `runHost(emptyArray())`，因为 Host `main` 现在带 `args`。
- `plugin.json` 的 version 是 `0.1.0`，包名是 `0.1.0-SNAPSHOT`，暂未统一。
- Host 默认会打印 `embedded host.txt`，这是临时验证输出，后续启动器接入时会替换。
- `FileZipClasspath` 的条目读取每次打开文件；语义正确，但高频读取可以后续做句柄复用。
- cinterop 对不完整结构体生成 `cnames.structs.*`，IDE 的 KMP 中间源集索引不到。
  `KeelQueueTag` 因此用 `KEEL_CINTEROP` 占位完整定义；改 ABI 头文件时别把宏分支删掉，
  除非 Kotlin 真的需要按值 / 按布局使用该类型。
- 新增事件 kind 要同时改三处：`keel_abi.h` 枚举、`PluginWorker.dispatch`、`HostPump.drain`。
  只改头文件的话，事件会在两端被静默丢掉，没有日志、没有报错。
- 插件日志走 Host 收件箱（256 条），日志风暴时会被丢弃；排查「日志缺行」先怀疑队列满。
- 不要把 `plugin_id` 当稳定身份缓存或写盘：它每次启动按加载顺序重新分配（§3.8），
  持久化标识一律用 manifest 的 `id`。
- 插件侧 `PluginContext.metadata` 只有 `id` 有值；展示名由 Host 侧的 `PluginNames` 提供，
  别在插件里用 `metadata.name` 拼模块名（会是空串）。
- `PluginContextImpl` 的 `server` / `modules` / `config` / `scope` 是 `error(...)`：
  在 `onLoad` / `onEnable` 里访问它们会抛异常，`bootstrap` 返回 `KEEL_ERR_FAILED`，
  外部表现是「插件启动失败」而不是「功能尚未实现」。
- `--serve`（不限时）只能靠杀进程结束：不会执行插件 `onDisable`，也不会 drain 最后的日志；
  冒烟与演示用 `--serve-ms=<n>`，它会走完整的 shutdown 流程。
- `Scheduler.schedule` / `TaskHandle.cancel` 只能在 Worker 线程调用；任务表无锁，
  从别的线程调用会与 `tick` 竞争，`keel_plugin_set_wakeup` 也假定单写者。
- 周期任务里做长耗时同步操作会占住 Worker 线程：事件分发、其它任务、PING 回包都会排队，
  长任务应拆成多次短任务或交给协程（`ctx.scope` 尚未实现）。
