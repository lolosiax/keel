## 1. 项目定位

- **Keel**：Kotlin/Native 的模块化 Web 框架，心智模型是 Tomcat/WAR + Bukkit/Spigot。
- Host 是容器；插件是部署单元；目标平台 `mingwX64`、`linuxArm64`（RK3566）、`linuxX64`。
- 硬约束来自 [前序讨论.md](前序讨论.md)：
  - K/N 运行时不可安全卸载；
  - Host 与插件是两个运行时，只能传 blittable / 句柄 / 事件；
  - 协程与调度器不跨 C ABI；
  - 热路径用 CBOR/Protobuf，不用 JSON。

## 2. 当前目录与构建

根 `settings.gradle.kts` 的 includeBuild：

```
keel-classpath-gradle-plugin
keel-abi-gradle-plugin
keel-plugin-gradle-plugin
keel-publish-gradle-plugin
keel-router-ksp
keel-classpath
keel-abi
keel-classpath-full
keel-api
keel-host
keel-launcher
keel-plugin-hello
```

每个目录都是独立 Gradle 构建；单独构建时用 `gradlew -p <目录> <任务>`。
跨目录依赖走 Maven 坐标；本地验证时用 `--include-build=...` 提供被依赖工程。

### 2.1 本机 Gradle 注意事项

- 机器代理 `localhost:33210` 经常没在监听；所有命令加：
  ```powershell
  "-Dhttp.proxyHost=" "-Dhttps.proxyHost="
  ```
  ⚠️ PowerShell 会把不带引号的 `-Dhttp.proxyHost=` 拆成两个参数，报
  `Task '.proxyHost=' not found`，必须加引号。
- includeBuild 多、K/N 链接重时可能 `Metaspace`；先 `gradlew --stop`，
  再加 `-Dorg.gradle.jvmargs=-Xmx4g`。

## 3. 已完成

### 3.1 `keel-classpath`（独立资源库）

包名 `moe.lolosia.keel.classpath`，不依赖 `keel-api`。

| 文件 | 作用 |
| --- | --- |
| `Classpath.kt` | 只读资源接口 + `ClasspathResource` + `of(pluginId)` 默认 fail-closed |
| `ClasspathNotFoundException.kt` | 命名空间卸载 / 不存在 |
| `ByteArrayClasspathResource.kt` | 默认流式句柄 |
| `PrefixedClasspath.kt` | `.keel` 的 `resources/` 前缀视图 |
| `DiskClasspath.kt` | 目录回退 |
| `ZipClasspath.kt` | 内存映像 zip（嵌入模式） |
| `ZipFileClasspath.kt` | 文件型 zip：只读 EOCD / 中央目录 / 目标条目 |
| `RandomAccessFile.kt` + linux/mingw actual | 平台随机读 |
| `ZipInflate.kt` | 共享 raw deflate |
| `EmbeddedClasspath.kt` + linux/mingw actual | 读取内嵌 `classpath.zip` |
| `installEmbeddedClasspath()` | 普通可执行文件安装内嵌资源；`KEEL_CLASSPATH_DIR` 可切目录 |

### 3.2 `keel-classpath-full`（Host 注册表 / 跨模块）

| 文件 | 作用 |
| --- | --- |
| `ClasspathRef.kt` | 绑定插件 id + generation，不暴露 `.keel` 路径 |
| `ClasspathRegistry.kt` | Host 注册表接口 + `pluginClasspath(registry, id)` |
| `DefaultClasspathRegistry.kt` | 注册 / 卸载 / generation 失效 |
| `GuardedClasspath.kt` | 每次读取校验代次；卸载后抛异常 |
| `CompositeClasspath.kt` | 自身优先 → Host 回落；`of(id)` 显式跨插件 |
| `RegistryClasspath.kt` | Host 自己的资源 + `of(id)` |
| `ClasspathTransport.kt` | 跨运行时读取抽象 |
| `RemoteClasspath.kt` | 插件侧远程引用 + `remotePluginClasspath` |
| `HostClasspathTransport.kt` | Host 侧把请求落到注册表 |

### 3.4 Gradle 插件 / 构建期工具

每个构建期工具都是顶层独立构建，一个构建只产出一个插件 ID：

| 工程 | 插件 ID / 产物 | 作用 |
| --- | --- | --- |

### 3.7 `keel-abi`（C 实现 + 静态库）

全新顶层构建，`src/nativeCpp/` 里放 ABI 的实现，`keel_abi.h` 也在这里（唯一布局来源）。

| 文件 | 作用 |
| --- | --- |
| `keel_abi.h` | 事件 / 状态码 / 函数表 / 导出入口；`KEEL_EXPORT` 只给 bootstrap、shutdown |
| `keel_queue.c` | 定长环形缓冲，节点一次性预分配，push/pop 带超时 |
| `keel_event.c` | `keel_event_release_default`（按发送方 CRT free） |
| `keel_plugin.c` | `bootstrap`（纯 C，起泵线程）/ 泵循环 / START 握手 / `shutdown` |
| `keel_platform.h` | mingw 用 `CRITICAL_SECTION` + `CONDITION_VARIABLE` + `CreateThread`；linux 用 pthread |

任务：`keelAbiObjects<target>` → `keelAbiArchive<target>` → `keelAbiPackage`，
产物 `libkeel_abi.a` + `include/keel_abi.h` 打进 `keel-abi-<version>.zip`。
默认只编主机目标（K/N 下载的 linux gcc 是 Linux 可执行文件），
跨目标用 `-Pkeel.abi.targets=linuxX64`。

`moe.lolosia.keel.abi`（`keel-abi-gradle-plugin`）负责解包 + `linkerOpts("-L…", "-lkeel_abi")`：
Host 在 `build.gradle.kts` 显式 `id("moe.lolosia.keel.abi")`，
插件工程由 `moe.lolosia.keel.plugin` 自动 apply。
`keel-plugin-gradle-plugin` 因此依赖 `keel-abi-gradle-plugin`——
`pluginManager.apply(id)` 只查 buildscript classpath，不查 `pluginManagement.includeBuild`。

### 3.8 Host 插件加载器（Kotlin 部分）

`keel-host` 的 `host/plugin/`：

| 文件 | 作用 |
| --- | --- |
| `PluginLoader.kt` | 扫描目录、校验 manifest、解出动态库、注册 classpath；`loadAll` 把失败隔离成 `PluginLoadFailure` |
| `LoadedPlugin.kt` | 已可 `dlopen` 的插件：manifest + 缓存里的库路径 + `ClasspathRef` |
| `PluginLoadFailure.kt` / `PluginLoadResult.kt` | 单条失败原因 / 一轮扫描结果 |
| `PluginFs.kt` | 最小文件读写（查大小、覆盖写） |
| `HostTarget.kt` | 运行期目标名 `mingwX64` / `linuxArm64` / `linuxX64`，用于选 `lib` 条目 |
| `package.native.kt` | `listNames`，mingw 与 linux 共用 posix `opendir` |
| `package.mingw.kt` / `package.linux.kt` | `mkdirs`：mingw 的 `mkdir` 只有一个参数，linux 是 path + mode |

CLI：`keel-host --plugins <目录> [缓存目录]`，缓存默认 `<目录>/.cache`，
库落到 `<cache>/<id>/<version>/<文件名>`；**同名同大小不重写**（避免覆盖已映射的库）。

校验顺序：manifest 可读 → id 非空 → `abiVersion == 1` → id 不重复 → 当前目标有 `lib` 条目
→ 包内确实有该库 → `entry` 非空。`sha256` 尚未校验。

## 5. 已确认的设计决策

1. **Classpath 只做资源**，不是类加载；K/N 不能跨插件加载类。
2. 插件包是 `.keel`（zip）：根 `plugin.json`、`lib/<target>`、`resources/`。
3. 资源**不解包**；插件与 Host 都按 zip 随机读。
4. 插件读自己：本地 `.keel`；缺失回落 Host；跨插件只能 `ctx.classpath.of(id)`。
5. `.keel` 真实路径只在 Host；插件侧只拿 `ClasspathRef`，`origin` 为 `keel://<id>`。
6. 卸载以 Host 注册表为准：generation 失效，旧引用读取抛 `ClasspathNotFoundException`。
7. 普通 exe/dll/so 走原 `classpath.zip` 嵌入；插件 dylib 不嵌 `classpath.zip`。
8. `keel-classpath` 独立可用；`keel-api` 只依赖它的类型；`-full` 负责 Host 注册表与代理。
9. 插件侧 `ClasspathTransport` 尚未实现，等事件泵 / C ABI 落地。

## 6. 已知缺口 / 下一步

加载器的 Kotlin 部分已完成（§3.6）；**剩下全部卡在 C ABI 上**，顺序如下。

1. **C ABI（队列 / bootstrap 已完成，§3.7）**
   - 已做：队列、`release_default`、`bootstrap`（纯 C + 泵线程）、START 握手、`shutdown`；
     用纯 C 测试验证过：`bootstrap=0 → COMPLETE(corr=42, status=0) → shutdown`；
   - 还差：句柄表（`handle_new/retain/release` + DISPOSE）、载荷分配助手；
   - Kotlin 侧还没接：没有 `@CName` 的 `worker_main`，所以 `.a` 目前只是被链进去、没有被引用。

2. **把加载器接到 `dlopen`**
   - `LoadedPlugin.libraryPath` 就是待加载路径；
   - 调用 `keel_plugin_bootstrap`，传 `.keel` 路径、`resources/` 前缀、插件 id、数据目录；
   - 卸载时 `unregister` + 关闭 Host 侧句柄，dylib 不 unmap。

3. **`plugin.json.entry` 切到 `keel_plugin_bootstrap`**
   - hello 目前仍导出 Kotlin 工厂 `keel_plugin_hello_create`；
   - Host 不应直接调用它，必须由 bootstrap 在插件 Worker 上调用。

4. **插件侧 `ClasspathTransport`**
   - 用事件泵 / C ABI 实现 `ClasspathTransport`；
   - 把 `RemoteClasspath` / `remotePluginClasspath` 接到插件运行时；
   - `PluginContext.classpath` 目前只有接口，没有运行时实现。

其他缺口：

- `FileZipClasspath.lastModified` 仍是 null；后续按文件 mtime 补，`mmap` 可选。
- 普通 `SharedLibrary` 的嵌入未接（需要每模块 HMODULE / 唯一符号）。
- `.keel` 的 sha256 未校验；版本化文件名、Windows 清理未做。
- `KeelServer` / `PluginContext` 仍只有接口，没有 Host 实现类。
- 自动化测试没有；目前靠 `--inspect` 与 Host 启动输出验证。

## 7. 易踩的坑

- `keel-classpath-full` / `keel-api` 现在依赖 `keel-classpath`；单独 `-p` 构建必须带
  `--include-build=../keel-classpath`，否则去 Maven 找不到。
- `keel-plugin-hello` 自动依赖 `keel-classpath-full`；单独构建必须带
  `--include-build=../keel-classpath-full`。
- K/N 2.4 里 `kotlinx.cinterop.toWideString` 已不存在；要调 Windows 的 `W` API 得自己
  `allocArray<WCHARVar>` 拼 UTF-16。实测 mingw 的 `platform.posix` 有 `opendir` / `readdir`，
  但 `mkdir` 只有 path 一个参数（linux 是 path + mode），两端签名不同，必须 expect/actual。
- `keel-host` 的 `settings.gradle.kts` 通过 `pluginManagement.includeBuild` 引入
  `../keel-classpath-gradle-plugin`；`keel-plugin-hello` 引入 `../keel-plugin-gradle-plugin`。
  改插件后要重新构建插件，Gradle 会自动处理。
- 构建期工具各自带一份发布仓库配置；`local.properties` 始终按 `../local.properties` 找，
  单独 clone 某个构建时它必须与仓库根同级。
- `keel-launcher` 调用 `runHost(emptyArray())`，因为 Host `main` 现在带 `args`。
- `plugin.json` 的 version 是 `0.1.0`，包名是 `0.1.0-SNAPSHOT`，暂未统一。
- Host 默认会打印 `embedded host.txt`，这是临时验证输出，后续启动器接入时会替换。
- `FileZipClasspath` 的条目读取每次打开文件；语义正确，但高频读取可以后续做句柄复用。
