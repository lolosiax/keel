## 1. 项目定位

- **Keel**：Kotlin/Native 的模块化 Web 框架，心智模型是 Tomcat/WAR + Bukkit/Spigot。
- Host 是容器；插件是部署单元；目标平台 `mingwX64`、`linuxArm64`（RK3566）、`linuxX64`。
- 硬约束来自 [前序讨论.md](前序讨论.md)：
  - K/N 运行时不可安全卸载；
  - Host 与插件是两个运行时，只能传 blittable / 句柄 / 事件；
  - 协程与调度器不跨 C ABI；
  - 热路径用 CBOR/Protobuf，不用 JSON。
- 目录角色、依赖方向与构建 / 发布约定见 [../AGENTS.md](../AGENTS.md) §0–§7。

## 5. 已确认的设计决策

1. **Classpath 只做资源**，不是类加载；K/N 不能跨插件加载类。
2. 插件包是 `.keel`（zip）：根 `plugin.json`、`lib/<target>`、`resources/`。
3. 资源**不解包**；插件与 Host 都按 zip 随机读。
4. 插件读自己：本地 `.keel`；缺失回落 Host；跨插件只能 `ctx.classpath.of(id)`。
5. `.keel` 真实路径只在 Host；插件侧只拿 `ClasspathRef`，`origin` 为 `keel://<id>`。
6. 卸载以 Host 注册表为准：generation 失效，旧引用读取抛 `ClasspathNotFoundException`。
7. 普通 exe/dll/so 走原 `classpath.zip` 嵌入；插件 dylib 不嵌 `classpath.zip`。
8. `keel-classpath` 独立可用；`keel-api` 只依赖它的类型；`-full` 负责 Host 注册表与代理。
9. `ClasspathTransport` 接口与 Host 侧实现已落地；插件侧（经事件泵 / C ABI）的远程实现尚未接。
10. **Host 的 Ktor 与事件泵是两个执行者，不需要合并**：Ktor handler 用
    `suspendCancellableCoroutine` 把请求投给事件泵并挂起，泵线程收到 COMPLETE 后按
    correlation resume；`ApplicationCall` / `Continuation` 只留在 Host 运行时，绝不跨 ABI。
    实现是 `Channel<HostRequest>` + `CompletableDeferred`：pending 表只由泵线程读写，
    外部线程不碰它。
11. **单 exe = 预编译 launcher + 注入的 bundle**：用户工程始终保持插件工程形态，
    不声明 application / executable；bundle 用 PE 资源（Windows）或文件尾 trailer（Linux）携带，
    运行期只在内存打开，同 id 以磁盘 `plugins/` 优先。

## 6. 已知缺口 / 下一步

加载、握手与 C ABI 的主链路已打通（§3.7 / §3.8）；M1 的九项运行时前置也已完成
（[basic-stack-design.md](basic-stack-design.md) §12）。**当前主线：M2（rbac 与 biz），
只完成契约与数据库能力链路，表结构、仓库层与两个业务插件都还没开始。**

§6.1 / §6.2 保留为 M1 之前的缺口快照；已完成或已变化的条目已就地标注，没标注的仍然有效。

### 6.1 主线待办

1. **事件分发与路由（Host→插件→Host 已闭环）**
   - 已做：Host 按 `target` 转发到插件 inbox（`registerPluginInbox` + `popHostEventRaw`）；
     两端未处理事件各告警一次；`host_inbox` 改成普通指针，消除插件线程调用 Host Kotlin；
     Host 用 `requestPlugin` + `KEEL_SUBJECT_PING` 跑通一次请求 / 应答与 correlation 配对（§4.4）。
   - 还差：插件侧主动发起事件的 API（拿目标 id、构造载荷、选择 kind）；
     调度器（§4.5）已提供启动后的触发点，补上发送 API 就能跑插件间消息。
   - Host→插件的**带载荷请求 + 异步桥接**已完成：`HostPump.request`（Channel +
     `CompletableDeferred`）可在 Ktor 线程发起，泵线程回投；`/ping` 已端到端验证（§4.6）。
   - Host 常驻循环已具备：`--serve` / `--serve-ms=<n>`，主线程单线程 drain，无额外线程。
   - 已完成（M1-1）：`RouteDescriptor` 路由注册与 `keel-router-ksp` 实装；
     插件侧主动发事件（M1-4）也已由 `ctx.host.post/request` 提供。

2. **C ABI 句柄表**
   - `KeelHostApi.handle_new/retain/release` 恒为 null，`KEEL_EVENT_DISPOSE` 没有产生方；
   - 需要句柄表、引用归零投 DISPOSE、插件侧释放路径；
   - 这是 P0 `@ModuleService` 生成跨模块代理的前置条件。

3. **业务载荷格式**（大部分已完成）
   - 跨模块服务、Host 反向请求与存储统一用 CBOR 信封（`ServiceWire` + 各 DTO）；
   - 句柄列表与两阶段批量序列化仍未做。

4. **插件侧 `ClasspathTransport`**
   - Host 侧 `HostClasspathTransport` 已通；插件侧要经事件泵向 Host 注册表取资源；
   - `PluginContext.classpath` 目前是 `EmptyClasspath`，`RemoteClasspath` / `remotePluginClasspath`
     没接运行时。

5. **插件 id 与元信息**
   - Host 侧 `KeelPackageManifest.toMetadata()` 已能给出 id / name / version / entry /
     authors / color；但插件运行时仍只有 `plugin_id`（`PluginMetadata.name` / `version` /
     `entry` 是空串），需要把 manifest 元信息下发到 Worker。

6. **Linux 导出验证**
   - `.def` 只在 mingw 生成；linux 上 `@CName` 符号是否进 `.dynsym`（默认 visibility）未实测，
     需要在板子上跑一次 `dlopen` + `dlsym`，不行就加 version-script / `--dynamic-list`。

7. **MariaDB 真实后端（M2 前置）**
   - `keel-database-mariadb` 目前只响应 `select 1`，其余语句返回 `KEEL_ERR_UNSUPPORTED`；
     表结构、仓库层与 rbac / biz 都依赖真实 `libmariadb` 接入（只需替换 `backend_*`）。

8. **M2 业务插件**
   - 表与迁移、`permissions.yaml`、手写仓库层、`keel-plugin-rbac`、`keel-plugin-basic-biz`
     均未开始；目录当前不存在，接口只在两个 `-api` 契约库里。
