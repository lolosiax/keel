### 3.7 `keel-abi`（C 实现 + 静态库）

全新顶层构建，`src/nativeCpp/` 里放 ABI 的实现，`keel_abi.h` 也在这里（唯一布局来源）。

| 文件 | 作用 |
| --- | --- |
| `keel_abi.h` | 事件 / 状态码 / 函数表 / 导出入口；`KEEL_EXPORT` 只给 bootstrap、shutdown |
| `keel_queue.c` | 定长环形缓冲，节点一次性预分配，push/pop 带超时 |
| `keel_event.c` | `keel_event_release_default`（按发送方 CRT free） |
| `keel_plugin.c` | `bootstrap`（纯 C，起泵线程）/ 泵循环 / START 握手 / `shutdown` |
| `keel_platform.h` | mingw 用 `CRITICAL_SECTION` + `CONDITION_VARIABLE` + `CreateThread`；linux 用 pthread |

任务：`keelAbiObjects<target>` → `keelAbiArchive<target>` → `keelAbiPackage`，
产物 `libkeel_abi.a` + `include/keel_abi.h` 打进 `keel-abi-<version>.zip`。
默认只编主机目标（K/N 下载的 linux gcc 是 Linux 可执行文件），
跨目标用 `-Pkeel.abi.targets=linuxX64`。

`moe.lolosia.keel.abi`（`keel-abi-gradle-plugin`）负责解包 + `linkerOpts("-L…", "-lkeel_abi")`：
Host 在 `build.gradle.kts` 显式 `id("moe.lolosia.keel.abi")`，
插件工程由 `moe.lolosia.keel.plugin` 自动 apply。
`keel-plugin-gradle-plugin` 因此依赖 `keel-abi-gradle-plugin`——
`pluginManager.apply(id)` 只查 buildscript classpath，不查 `pluginManagement.includeBuild`；
这个依赖靠 `keel-plugin-gradle-plugin/settings.gradle.kts` 里的
`pluginManagement.includeBuild("../keel-abi-gradle-plugin")` 在 composite 下替换成本地工程。

sharedLib 额外做两件事（Kotlin 侧不做任何标注）：

- `-u keel_plugin_bootstrap`：Kotlin 代码从不引用静态库成员，不强制拉入就没有泵线程；
- 生成 `build/generated/keel-abi/<target>-def/keel-plugin.def` 并作为链接输入：
  Kotlin 的 `@CName` 符号**不会**自动进 PE 导出表，Host 会 `dlsym` 不到。
  默认导出 `keel_plugin_bootstrap` / `keel_plugin_shutdown` / `keel_plugin_worker_main`
  以及分步关闭的三个符号 `keel_plugin_request_shutdown` / `keel_plugin_pump_running` /
  `keel_plugin_join`；用别的入口名时 `keelAbi { export("...") }` 追加。

`KeelQueueTag` 在头文件里用 `KEEL_CINTEROP` 分成两支：cinterop 侧看到只有 `void *reserved` 的
**完整占位结构体**（宏由 `keelabi.def` 的 `compilerOpts` 注入），C 实现侧仍只看到前向声明。
这样 cinterop 把类型生成到 `moe.lolosia.keel.abi.c`，而不是 IDE 中间源集索引不到的
`cnames.structs`。Kotlin 侧只能持有指针，不能解引用、分配、按值传递或 `sizeof`。

日志事件：`KEEL_EVENT_LOG` + `KeelLogLevel`（TRACE / DEBUG / INFO / WARN / ERROR / FATAL）。
插件用 `keel_payload_alloc` / `keel_payload_copy` 写 UTF-8 载荷，并挂上本二进制的
`keel_event_release_default`；Host 在 `popHostEvent` 里复制载荷后再 release。

健康检查：`KEEL_SUBJECT_PING` 是最小请求 / 应答回路——Host 向插件投
`COMMAND{subject=PING, correlation=N}`，插件回 `COMPLETE{correlation=N, status=OK}`。
Host 在每个插件启动完成后体检一次（`ping <id> ok`），这是目前唯一在运行期跑通的往返路径。

调度器定时：`keel_plugin_set_wakeup(delayMs)` 设置泵线程下一次 pop 的超时；到点且 inbox 为空时，
C 侧投一条 `COMMAND{subject=KEEL_SUBJECT_TIMER}` 给插件分发表，由 `WorkerScheduler.tick()`
在同一个 Worker 线程上跑到期任务并重新定时。delay < 0 表示取消定时。

### 3.8 Host 插件加载器（Kotlin 部分）

`keel-host` 的 `host/plugin/`：

| 文件 | 作用 |
| --- | --- |
| `PluginLoader.kt` | `scanDirectory` 只读 manifest；`load(PluginPackage)` 校验、解出动态库、注册 classpath；失败隔离成 `PluginLoadFailure` |
| `PluginPackage.kt` + `FilePluginPackage` / `BundlePluginPackage` | 磁盘 `.keel` 与内嵌 bundle 条目的统一视图（origin / manifest / classpath / read） |
| `PluginBundle.kt` / `PluginScan.kt` | 扫描内嵌 `plugins/<id>/plugin.json`；目录扫描结果（包 + 失败） |
| `LibraryCache.kt` | 把 `.keel` 内动态库落到缓存目录；总是重写，文件被占用时换名 |
| `LoadedPlugin.kt` | 已可 `dlopen` 的插件：manifest + 缓存里的库路径 + `ClasspathRef` |
| `PluginLoadFailure.kt` / `PluginLoadResult.kt` | 单条失败原因 / 一轮扫描结果 |
| `NativeLibrary.kt` + `.mingw.kt` / `.linux.kt` | `LoadLibraryA`/`GetProcAddress` 与 `dlopen`/`dlsym`；不提供 close（K/N 运行时不可卸载） |
| `HostAbi.kt` | 进程内收件箱 `keel_queue_create` + `KeelHostApi` 表；`popHostEvent` 复制标量与载荷后归还 |
| `LogEvent.kt` / `HostPump.kt` / `PluginNames.kt` | 日志事件解码、收件箱 drain（按 `target` 转发）、`plugin_id` → manifest id |
| `PluginRuntime.kt` | `startPlugin`：bootstrap → 投 START → 等 COMPLETE；`shutdown()` 先 `request_shutdown`，边 `HostPump.serve` 边等泵线程退出（上限 5s），再 `join` |
| `PluginFs.kt` | 最小文件读写（查大小、覆盖写） |
| `HostTarget.kt` | 运行期目标名 `mingwX64` / `linuxArm64` / `linuxX64`，用于选 `lib` 条目 |
| `package.native.kt` | `listNames`，mingw 与 linux 共用 posix `opendir` |
| `package.mingw.kt` / `package.linux.kt` | `mkdirs`：mingw 的 `mkdir` 只有一个参数，linux 是 path + mode |

CLI：`keel-host --plugins <目录> [缓存目录] [--once] [--http=<端口>] [--serve-ms=<n>]`，
缓存默认 `<目录>/.cache`，库落到 `<cache>/<id>/<version>/<文件名>`；
**每次启动都重写**；目标文件被占用时退到 `name.1.dll` / `name.2.dll` 换名加载
（`LibraryCache.kt`，插件与能力包共用）。
加载成功后会逐个启动并 ping 体检；**默认常驻**（主线程进入事件循环），
`--once` 表示体检后立即退出（自动化用），`--serve-ms=<n>` 表示服务 n 毫秒后退出，
`--http` 启动 Host 自己的 Ktor CIO。
进程退出时先停 HTTP，再逐个 `shutdown()`；单个插件启动失败只打印原因，不影响其它插件。

日志：Host `Log` 统一格式 `HH:mm:ss 级别 模块 来源 : 消息`；
模块列默认 15（Host / 插件名 / 自定义 tag），来源列默认 40（`短类名:行号`）。
启动时打印版本、可执行文件、pwd、OS/架构、target、ABI；loader 只打印
`<keel>!/<包内库路径>`、插件名、版本与作者，不再打印实际 cache 路径。

校验顺序（`PluginLoader.load`）：manifest 可读 → `id` 非空 → `abiVersion == 1` → `entry` 非空
→ `id` 不重复 → 当前目标有 `lib` 条目 → 包内确实有该库。
`sha256` 只被读进 `PluginClasspathEntry`，尚未校验。

联调必须知道的运行时事实：

- `plugin_id` 由 Host 从 1 开始按加载顺序自增，**只在当前进程内有效**，重启后重排，
  也不写进 manifest；`PluginNames` 用它把日志里的 id 映射回插件名。
- 单个插件启动超时 5000ms；等待某插件 `COMPLETE` 期间，其它插件的非 `KEEL_EVENT_LOG`
  事件会被直接丢弃。
- Host 收件箱容量 256 条；插件侧 inbox 同样是 256（`keel_plugin.c` 的 `KEEL_INBOX_CAPACITY`）。
- `KeelHostApi.handle_new/retain/release` 全部为 `null`，插件无法申请跨运行时句柄。
- 插件侧 `PluginMetadata` 只有 `id` 有值（`plugin_id.toString()`），`name` / `version` / `entry` 是空串。
- `KeelHostApi.host_inbox` 是**普通指针字段**，不是函数指针：插件在自己的 Worker 线程上读取它
  不会进入 Host 运行时。早先的函数指针写法会让插件线程调用 Host Kotlin，违反线程模型，已修。
- 转发按 `target` 字段走：`target == 0` 表示 Host，其它值必须在 `pluginInboxes` 里查得到，
  否则事件告警一次后丢弃；转发成功后载荷所有权交给目标插件，Host 不再 release。

### 3.9 日志调用点（keel-logger）

`keel-api` 新增 `Log` 门面与 `LogSite` / `LogSiteKind` / `LogSink` / `LogSiteCodec`。
`moe.lolosia.keel.logger`（Gradle 插件 + 编译器插件）在 IR 阶段把
`Log.info(xxx)` 改写成 `Log.of(displayName, file, line, packageName, className, functionName, kind).info(xxx)`。

- `displayName`：类内为完整类名；类外为 `包名.文件名首字母大写 + Kt`。
- `file`：相对 Gradle 调用目录的路径；Gradle 插件传 `workspaceRoot` + `sourceRoot`，
  编译器插件按 `包名/文件名` 反查（IR 只暴露文件名）。
- Host `HostLogSink`：时间只保留 `HH:mm:ss`；模块列默认 15（`Log.moduleWidth`），
  来源列 `短类名:行号` 默认 40（`Log.displayNameWidth`）。
- 来源列压缩：保留类名，包段先各 1 字，再从右往左逐级加长直到用满预算；
  仍放不下才从左丢段并加 `…`（例：`moe.lolo.keel.plugi.hello.HelloPlugin:18`）。
- 颜色：Host 启动时探测 stdout（Win32 `GetConsoleMode` + VT、Linux `isatty` + `TERM`）；
  配色（整段时间默认色；TRACE 亮灰、DEBUG 浅蓝、INFO 绿、WARN 黄、ERROR 红、
  FATAL 红底黑字；来源类名 cyan、`:行号` faint），模块名用 FNV-1a 哈希取 12 色盘
  （普通 6 色 + 亮色 6 色）。
  `plugin.json` 的 `color`（`#RRGGBB` / `#RGB`）优先于哈希色，走 ANSI truecolor
  （`38;2;r;g;b`）；颜色非法时回落到哈希并打一条 Loader 警告。
  支持 `NO_COLOR` / `CLICOLOR=0` 关闭与 `FORCE_COLOR` 强制开启。
- 模块名：Host 日志默认 `Host`，插件日志默认用 manifest `logTag`（留空回落 `name`、再 `id`），
  显式 `tag = "Loader"` / `tag = "EventBus"` 可自定义；模块列按终端显示宽度补齐（CJK 记 2 列）。
- 插件 `NativePluginLogger`：有 `LogSite` 时用 `LogSiteCodec` 编码模块名与来源进
  `KEEL_EVENT_LOG`，Host 解析后按模块 + 插件侧类名展示；`ctx.logger` 仍是纯文本。
- 自动接线：`moe.lolosia.keel.plugin` 自动 apply logger；`keel-host` / `keel-launcher`
  显式 `id("moe.lolosia.keel.logger")`。`keel-api` 自身不挂（库不依赖构建期插件），
  因此 `PluginWorker` 里的兜底错误日志没有调用点。

**异常诊断**（同一编译器插件）：

- `IrConstructorCall`（`Throwable` 子类）与 `IrThrow` 两处插桩，把
  `类.函数(File.kt:行)` 写入 `ThrowTrace` 侧表（容量 64、60 秒 TTL、按对象身份 `===` 匹配）；
  `toKeelError()` 编码完成后 `release`。
- 日志渲染 `StackTraceFormat` 在每层异常头后输出
  `Created at / Throwed at / Printed at`，诊断行与栈帧之间空一行；`Printed at` 只对最外层输出。
- 跨运行时走 `KeelErrorEntry.createdAt / throwSites`；Host 用 `RemoteThrowable` 标记远端异常，
  只渲染 `toString()`，不再追加 `KeelRemoteException.<init>` 这类载体栈。

**`Log.site()`**：占位函数（默认返回 null），插件把它替换成真实的 `Log.of(...)`。
用于「自定义来源列但仍要调用点」的场景（如 HTTP 错误日志），也可以单独取用；
未应用插件的模块拿不到，`inline` 函数里记录的是 inline 体内的行号。

**插件作用域**：IR 扩展只在**当前编译模块**上跑一次，依赖 klib 不会在消费端重打；
klib 里的站点取决于它自己编译时有没有应用插件。非 inline 函数消费端看不到函数体，
inline 函数体由 klib 原样带入，消费端也不会重新扫描。

### 3.10 运行时行为边界（当前实现只到哪）

这些是代码里真实行为、但接口看不出来的地方，接新功能前必须知道：

- 插件侧 `PluginWorker.dispatch` 处理 `SHUTDOWN`，以及 `COMMAND` 下的 PING / TIMER / HTTP /
  CONSOLE / SERVICE_CALL / AUTHN / AUTHZ；其余 kind / subject 每种告警一次后丢弃。
- Host 侧 `HostPump.dispatch` 按 kind 分派：LOG 就地消费；COMPLETE 按 correlation 完成请求或转发；
  ROUTE_REGISTER / SERVICE_REGISTER / SERVICE_CALL 与 `subject >= 0x1000` 的业务请求由 Host 处理；
  `target != 0` 的事件转发到目标插件 inbox；其余告警一次后丢弃。
- `HostPump.requestPlugin` 是 Host 发起的同步请求：投 COMMAND 后阻塞等待同 correlation 的
  COMPLETE（默认 2000ms），等待期间仍会消费其它事件；START / SHUTDOWN / PING 都走它。
- 插件侧主动发事件与反向请求由 `ctx.host`（`HostLink.post/request`，M1-4）提供；
  请求在 Worker 上重入事件泵等待，默认 3s 超时。
- 调度器任务只在 Worker 线程执行：泵线程按最近截止时间超时唤醒并投 `KEEL_SUBJECT_TIMER`；
  C 侧用 `keel_now_ms()` 计时，Kotlin 侧用 `TimeSource.Monotonic` 记截止时间，两者只传相对毫秒。
- `schedule` / `cancel` 只能在 Worker 线程调用；取消不会提前唤醒（最多空跑一次），
  周期任务落后超过一个周期时跳过积压，不补跑。任务抛异常只记日志，不中断泵线程。
- 插件日志在收件箱满时静默丢弃：`NativePluginLogger` 会归还载荷，但不报错、不打点。
- `PluginWorker.plugin` 是单例，没有重入保护：重复 START 会覆盖实例，且不调用旧实例的 `onDisable`。
- 卸载只让资源引用失效（`HostClasspath.unregister`），不 `dlclose`；`PluginLoader.unload` 目前没有调用点。
- 默认常驻：启动完成后主线程进入 `HostPump.serve()` 循环（200ms 超时）；
  `--once` 才在启动、体检后退出，`--serve-ms=<n>` 服务固定时长后走优雅 shutdown。
  不限时模式只能靠杀进程结束，不会执行插件 `onDisable`，也不会 drain 最后的日志。
- Ktor 引擎（`HostHttp`）跑在 Host 自己的线程 / 协程上，与事件泵是**两个执行者**，不需要合并：
  `/ping` 已走完整往返——handler 调 `HostPump.request` 挂起，请求经 Channel 交给泵线程，
  泵线程收到 COMPLETE 后按 correlation 完成 `CompletableDeferred`；`ApplicationCall` /
  `Continuation` 不跨 ABI。`/healthz` 不经过插件。
- `HostPump.request` 是 `suspendCancellableCoroutine` 的等价语义：Channel 负责跨线程交棒，
  pending 表只由泵线程读写（无锁），超时由 `withTimeoutOrNull` 与 deadline 双重清理。

### 3.11 插件 HTTP 路由（KSP 生成 + 手工注册）

链路：插件 `onLoad` 里 `ctx.routes.register(RouteDescriptor(...)) { request, params -> ... }`
→ 启用时 `PluginRoutes.publish()` 把描述表以 `COMMAND{subject=ROUTE_REGISTER}` 发给 Host
→ Host 在启动等待期解析并存入 `HostRoutes`（`awaitComplete` / `requestPlugin` / `drain`
都会消费这类事件，否则会被当成无关事件丢掉）
→ Ktor catch-all 按 method + path 匹配，把 `HttpRouteRequest`（JSON）经 `KEEL_SUBJECT_HTTP`
投给插件 → 插件查表执行 handler，回 `HttpRouteResponse`（status / contentType / bytes）。

- 手工 API：`RouteDescriptor`、`Routes`、`HttpRouteRequest`、`HttpRouteResponse`
  （`keel-api` 的 `web/*`）；`PluginContext.routes` 是插件侧入口。
- 当前匹配是线性扫描，支持精确段与 `{name}` 段；Demo 规模足够。
- **`keel-router-ksp` 已实装（M1-1）**：`@Controller` / `@GET` 等生成同包的 `KeelPluginRoutes`，
  参数绑定、JSON 信封与权限节点一并生成；手工 `ctx.routes.register` 仍然可用。
- 流式响应（`ResponseBody.Stream`）尚未接入，返回时降级为一段说明文本。

### 3.12 HTTP 访问日志

`HostHttp` 在 `ApplicationCallPipeline.Monitoring` 上装了入站 / 出站日志
（对应 med-agent 的 `LogWebFilter` / `ErrorWebFilter`）：

- 模块列（TAG）固定 `HTTP IN` / `HTTP OUT`，两者统一亮青色；状态码放在出站消息里，不占 TAG；
- 来源列换成客户端地址：IPv4 显示 `ip:port`（端口 faint 灰），IPv6 只显示地址，
  **不带方括号也不带端口**；IP 本身统一淡绿色；
- 出站级别按状态码：2xx/3xx INFO、4xx WARN、5xx ERROR；未捕获异常额外落一条 error
  （带堆栈）再抛回引擎；这条错误日志同样用客户端地址做来源列、沿用 HTTP OUT 的配色，
  并通过 `Log.site()` 保留 `Printed at` 调用点；
- 消息：入站 `METHOD /path`，出站 `METHOD /path - [status]  <耗时>ms`；
- 各跟一行**请求体 / 响应体**（截断到 200 字符，超出标注剩余长度）；请求体在
  Monitoring 阶段读一次存入 `call.attributes`，后续分发直接复用，避免二次读流。

实现走 `LogSink.logWithSource`（`Log.emitSource`）：同时给来源列的纯文本与 ANSI 版本，
`LogLineFormatter` 用纯文本算列宽、用 ANSI 版本着色；`moduleAnsi` 强制 TAG 颜色。
错误日志（`HttpLog.error`）也走这条路径，`site` 由 `Log.site()` 提供，因此
`Printed at` 不会因为换成客户端地址而丢失。

**延迟**：外部线程 `HostPump.request` 提交后必须投一条 `KEEL_SUBJECT_WAKE` 唤醒泵线程。
否则请求要等泵的 200ms 阻塞式 `pop` 超时才被处理——实测从 83~191ms 降到 3~8ms。

**Ktor 自身日志**（`Application started in ...` / `Responding at ...`）也并入同一套：
`HostHttp` 用自定义 `ApplicationEnvironment.log`（`KtorLogBridge`）替换默认的
`KtorSimpleLogger`，TAG 固定 `Ktor`，来源列显示 `io.ktor.server.Application`（无行号），
不会再出现 `[INFO] (io.ktor.server.Application): ...`。

### 3.13 构建期版本注入与启动横幅

Host 与插件都在构建时注入版本信息，启动时打印（不使用构建时间，保证同源码可复现）：

- Host：`generateBuildInfo` 生成 `moe.lolosia.keel.host.build.BuildInfo`
  （`VERSION` / `GIT_SHA` / `COMMIT_TIME` / `KOTLIN_VERSION` / `BUILD_ID = <version>-<sha>`）；
- 插件：`keelProcessManifest` 读取 `plugin.json`，合并 `buildInfo { gitSha, commitTime }`，
  输出到 `build/generated/keel/plugin.json`，`keelPackage` 打包这一份（源文件不改）。

启动信息集中在 `HostBootstrap`（在扫描插件之前打印），TAG 为 `Bootstrap`；
插件数量与单个插件的加载/启动状态由 `Loader` 输出；HTTP 入口、事件循环与停机
由 `HostRuntime` 负责，TAG 为 `Server`。

```text

INFO  Bootstrap  : executable: ...\keel-host.exe
INFO  Bootstrap  : working dir: ...
INFO  Loader     : loaded Hello Plugin (hello) v0.1.0 build e70855d (2026-11-07T22:37:45+08:00) by lolosia

职责边界：`Plugins.kt` 只做扫描、加载、启动与体检；跑起来之后的一切交给 `HostRuntime`。

### 3.14 中断与优雅停机

- C 侧 `keel_install_shutdown_hook()`：Windows 注册 `SetConsoleCtrlHandler`
  （Ctrl+C / Break / Close / Shutdown），POSIX 注册 `SIGINT` / `SIGTERM`；
  处理函数**只置一个原子标志**，不触碰 Kotlin；
- `HostRuntime` 的 serve 循环每轮（≤200ms）检查 `keel_shutdown_requested()`，
  置位后打印 `interrupt received`，然后停 HTTP → drain → 停插件（`onDisable` 期间仍
  `serve`，反向请求能拿到应答；泵线程 5s 不退就放弃 join）→ drain → 打印 `stopped N plugin(s)`；
- K/N 不能 `dlclose`：这里的“卸载”指退出流程，动态库仍留在进程地址空间。

实测方式：以 `CREATE_NEW_PROCESS_GROUP` 启动 Host，向进程组发 `CTRL_BREAK`，
进程在 1s 内以**退出码 0** 结束（若没有钩子，默认终止码是 `0xC000013A`）。

### 3.15 控制台与命令路由

- stdin 由 `keel-abi` 的 C 线程读取（`keel_console.c`）：Windows 终端用 `ReadConsoleW`
  再转 UTF-8（`fgets` 会按 ANSI 代码页解释，中文乱码），stdin 被重定向以及 Linux 用 `fgets`；
  整行写进 16 行环形缓冲，`keel_console_poll` 非阻塞取行，**读线程不进入 Kotlin**。
  `keel_console_start` 返回 stdin 是否为终端，Host 据此决定要不要画 `> ` 提示符。
- `HostConsole`（`keel-host/.../host/console/`）只在常驻模式启动，每轮主循环先取命令再
  `HostPump.serve()`；分发顺序照搬 Bukkit `SimpleCommandMap`：按空格拆分、label 转小写，
  先查 Host 命令表，未命中再按启用顺序逐个询问插件。
- Host 内置命令：`help`、`stop`（别名 `shutdown` / `exit` / `quit`）、
  `plugins`（别名 `pl` / `plugin`）。`plugins` 子命令：
  `list` / `info <id>` / `install <.keel>` / `remove|uninstall <id>` / `enable <id>` / `disable <id>`。
- 插件回调：`KEEL_SUBJECT_CONSOLE`（7）→ `PluginConsole` → `Plugin.onCommand(sender, command, label, args)`。
  输出经 `ConsoleCommandResult { handled, output }` 回投，Host 走 `Log`（TAG `Console`）输出，
  与其它日志共享格式与文件；交互式终端下 `ConsolePrompt` 常驻 `> `，日志行前 `\r` 回行首、
  行后补回提示符，非交互模式（管道 / `--once`）完全关闭提示符。
  退出时 `HostRuntime` 先 `ConsolePrompt.disable()` 擦掉提示符，停机日志不会再补 `> `。
  `handled = false` 继续问下一个插件，抛异常走错误信封（Host 打印错误链后继续）。
- `HostPlugins`（`keel-host/.../host/plugin/HostPlugins.kt`）持有安装清单与启停状态；
  扫描启动、控制台启停、退出停机共用这一份。`PluginRuntime.shutdown()` 之后再启动走
  `keel_plugin_bootstrap` 二次调用（C 侧 `memset` 重置、新建队列与泵线程），已实测可重入。
- 卸载语义：停用 → 清路由 / classpath → 删除包文件；K/N 不能 `dlclose`，动态库仍留在进程内，
  必须重启进程才释放。停用同时清掉该插件的路由；`PluginNames` 不复用数字 id 也不删除映射，
  晚到的日志仍能显示插件名。

### 3.17 单 exe 内嵌插件 bundle（2026-11-12）

- **构建期**：`moe.lolosia.keel.bundle` 由 `moe.lolosia.keel.plugin` 自动 apply，
  默认关闭（`keelPlugin.executable.enabled = false`）。开启后把本工程 `keelPackage` 产物 +
  `include(...)` 的 `.keel` 摊平成 `build/generated/keel/bundle/<target>/keel-bundle.zip`
  （`bundle.json` + `plugins/<id>/{plugin.json,lib/<target>,resources}`，同 id 直接失败），
  再注入**预编译 launcher 副本**，产物 `build/keel/<target>/<name>[.exe]`。
- **注入**：Windows 写 PE 资源（`.rc` → `windres -O res` → JNA `UpdateResource`，
  资源名 `IDR_KEEL_BUNDLE` / 类型 `KEELBUNDLE`）；Linux 在文件尾追加 32 字节 trailer
  （`offset` / `size` / `format=1` / `crc32` / `KEELBNDL`）。两边常量必须与
  `KeelExecutableTask` 一致。⚠️ windres 的 `.res` 里类型 / 名称是**无长度前缀的 UTF-16 串**，
  头部还有一个 `DataSize=0` 的空条目，解析时都要特殊处理。
- **launcher 工件**：`keel-launcher` 为每个目标注册 `keelLauncherPackage<Target>` Zip，
  发布 `keel-launcher-dev-<target>`；目前只有 debug（release Host 的 HTTP `ACCESS_VIOLATION` 未修）。
- **运行期**：Windows 从 PE 资源、Linux 从自身文件尾读 bundle，`ZipClasspath` 内存打开；
  `.keel` 与 `resources/` 不落盘，只有动态库物化到 `$root/.cache/<id>/<version>/`。
  加载顺序：磁盘能力 → 内嵌能力 → 磁盘插件 → 内嵌插件；两个来源装完才
  `validateDependencies()` + `activateDatabase()`。
- **同 id 优先级**：磁盘 `plugins/` 优先。磁盘 manifest 可解析即「认领」该 id，
  随后加载失败也不回退内嵌版本；运行时 `install` 覆盖已加载的内嵌插件会保留文件并要求重启
  （K/N 无法卸载已加载的库）。
- **工作根与端口**：`KEEL_HOME` → exe 目录 → 用户缓存目录；`plugins/` 与 `.cache/` 在其下。
  端口 `--http` > `KEEL_HTTP_PORT` > `application.yaml:server.port` > 7191（仅 bundle 模式默认开）。
  无参数且检测到内嵌 bundle 时默认常驻；`--once` / `--serve-ms=` 语义与 `--plugins` 一致。

### 3.18 `keel-plugin-console`（独立控制台窗口，2026-11-12）

设计见 [console-design.md](console-design.md)。三块拼起来：框架的 Messenger、helper 子进程、行编辑。

- **Messenger（框架）**：`Message` 改 `@Serializable`（`target` / `channel` / `payload` / `source`），
  `source` 由 Host 填；删掉 `correlationId`（配对改用 Host 的数字 correlation）。
  `Plugin.onMessage(message): ByteArray?` 默认 null；`correlation == 0` 表示通知、不回包。
  协议：`KEEL_SUBJECT_MESSAGE = 11`（Host → 插件），`HostSubjects.MESSAGE_POST = 0x100E` /
  `MESSAGE_REQUEST = 0x100F`（插件 → Host）；Host 按 manifest id 找目标、换 correlation 转发，
  `forwards` 表按 subject 泛化后兼做超时清扫。控制台插件用 `target = "console"`、`channel = "console"`。
- **helper（`src/nativeCpp/console_host.c`）**：纯 C，构建期用 K/N 自带 msys2 的 gcc + windres 编
  （`consoleHelper` 任务），产物以 `resources/native/keel-console-host.exe` 打进 `.keel`，
  运行时 `ctx.materialize(...)` 落地；`console_host.rc` 固定 `ProductName`/`FileDescription`
  为 `Keel Console`，图标用 keel 的 `keel-icon.ico`（副本放 `src/nativeCpp`，改 SVG 后要重新同步）。
- **通道**：两条单向命名管道 + 12 字节帧头（`KCN1` / version / type / length），
  `HELLO`(1) `OUT`(2) `IN`(3) `RESIZE`(4) `TITLE`(5) `CLOSE`(7)。不用 helper 的 stdin/stdout：
  `CREATE_NEW_CONSOLE` + `STARTF_USESTDHANDLES` 行为不稳定，会把 std 句柄从控制台挪走。
- **终端能力**：`OUT` 原样写 `CONOUT$`（UTF-8 码页 + `ENABLE_VIRTUAL_TERMINAL_PROCESSING`），
  helper 不解析 ANSI；颜色由 Host 侧用 `LogTextFormat.ANSI` 渲染，与插件 manifest 的 `color` 一致；
  日志行在插件里补 `\n`，helper 统一补 CRLF；启动时把 buffer 高度设为 `--scrollback`（默认 10000）。
- **输入**：不依赖 conhost 的 cooked 模式（见 §7）。`ReadConsoleInputW` 自己读按键、自己回显，
  支持 ←/→/Home/End/Delete/Backspace/Ctrl+W/Ctrl+U/Ctrl+C（清行）与 ↑/↓ 历史（64 条、去重、不落盘）。
  回显是整行重绘（`\r` + `ESC[2K` + `> ` 提示符 + 缓冲区 + 按显示宽度左移光标，CJK 按 2 列）；
  日志线程写前擦行、写完重绘，两者共用 `g_screen_lock`。
- **输入转发**：`IN` 帧 → 插件 `ConsoleInput.normalize`（去 CR/LF、丢空行、按 1023 字节且不劈 UTF-8）
  → `context.host.post(CONSOLE_INPUT)` → `HostConsole.inject` 写进与 stdin 同一条 16 槽环形缓冲
  → 下一轮 `poll()` 走正常命令分发。闭环成立是因为命令输出走 `Log`，又经 `Log.observe` 回到窗口。
- **命令**：`console open|close|reopen|status|title <text>|clear`（`onCommand` + 消息通道双入口）；
  标题在 `ConsoleState` 单例里跨窗口保留，默认 `Keel Console`，`open` 时作为 `--title` 传给 helper。
- **插件装配**：`plugin.json` id 为 `console`；只打 `mingwX64`；`config/plugins/console.yaml`
  有 `autoOpen` / `startId`(0 全量回放、-1 只看新的) / `maxReplayLines` / `scrollback` / `title` / `input`。

  --include-build=../keel-classpath --include-build=../keel-api `
  "-Dhttp.proxyHost=" "-Dhttps.proxyHost="

# host（含普通嵌入 + ABI 静态库）
gradlew -p keel-host linkDebugExecutableMingwX64 `
  --include-build=../keel-api --include-build=../keel-classpath `
  --include-build=../keel-classpath-full --include-build=../keel-abi `
  --include-build=../keel-logger-compiler-plugin `
  "-Dorg.gradle.jvmargs=-Xmx4g" "-Dhttp.proxyHost=" "-Dhttps.proxyHost="

# gradle 插件 / KSP
gradlew -p keel-logger-compiler-plugin build `
  "-Dhttp.proxyHost=" "-Dhttps.proxyHost="
gradlew -p keel-logger-gradle-plugin build `
  "-Dhttp.proxyHost=" "-Dhttps.proxyHost="
gradlew -p keel-classpath-gradle-plugin build `
  "-Dhttp.proxyHost=" "-Dhttps.proxyHost="
gradlew -p keel-plugin-gradle-plugin build `
  --include-build=../keel-abi-gradle-plugin `
  --include-build=../keel-logger-gradle-plugin `
  "-Dhttp.proxyHost=" "-Dhttps.proxyHost="
gradlew -p keel-publish-gradle-plugin build `
  "-Dhttp.proxyHost=" "-Dhttps.proxyHost="
gradlew -p keel-router-ksp build `
  "-Dhttp.proxyHost=" "-Dhttps.proxyHost="

# hello .keel
gradlew -p keel-plugin-hello keelPackage `
  --include-build=../keel-api --include-build=../keel-classpath `
  --include-build=../keel-classpath-full --include-build=../keel-abi `
  --include-build=../keel-plugin-ksp --include-build=../keel-logger-compiler-plugin `
  "-Dhttp.proxyHost=" "-Dhttps.proxyHost="
```

⚠️ 构建 `keel-abi` 的 C 源码前，必须把 K/N 自带的 mingw bin 放进 PATH，否则 gcc 静默失败：

```powershell
$env:PATH = "$env:USERPROFILE\.konan\dependencies\msys2-mingw-w64-x86_64-2\bin;$env:PATH"
```
