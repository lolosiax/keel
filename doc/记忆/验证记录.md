### 4.10 单 exe 冒烟（mingwX64，2026-11-12）

`keel-plugin-hello` 临时 `executable { enabled = true; name = "hello-app" }` 后
`gradlew -p keel-plugin-hello keelExecutableMingwX64`：

```text
hello-app.exe  25.4 MB（含 hello 的 .keel；PE 里能找到 KEELBUNDLE / IDR_KEEL_BUNDLE）
bundle: <exe>（1 个内嵌包，被磁盘覆盖 0 个）
source: embedded://plugins/hello!/lib/mingwX64/keel_plugin_hello.dll
resources: [hello.txt, web/index.html]
plugins: $KEEL_HOME/plugins    cache: $KEEL_HOME/.cache
ping hello ok   failed: 0   http listening on 0.0.0.0:7191
```

运行目录只有 `plugins/`（空）与 `.cache/hello/0.1.0/1/`（资源物化 + dll），没有 `.keel` 解压产物；
把 `.keel` 放进 `plugins/` 后重启：`被磁盘覆盖 1 个`，source 变为磁盘路径。
`--plugins <dir> --once` 旧模式回归正常。

已知限制：`gradlew -p keel-host build` / hello 的 `build` 在 Windows 上会在 `linuxArm64`
链接阶段报 `build/generated/keel-abi/linuxArm64/lib/linuxArm64` 不存在——`keel-abi` 的
`abiTargets` 默认只编宿主目标，zip 里没有 linux 静态库；只在 mingw 任务上验证。

### 4.11 第三方 codec 生成侧：Gradle 版 vs 旧 PS1 产物（2026-11-20）

`gradlew -p keel-thirdparty compileAll`（`gradle/codecs.gradle.kts`）产出 18 个归档，
与 `backend/build/thirdparty/out` 的 PS1 产物逐项对比：

```text
成员列表（llvm-ar t）      18/18 一致（合并后的 webp 都是 119 个成员）
导出符号（nm --defined-only）18/18 一致（mingw libwebp 1502、libjpeg 515；linuxX64 libwebp 1571 …）
公共头文件（sha256）        全部一致
文件大小                    15/18 逐字节等长
```

两处大小差异都有解释，不是行为变化：

- mingw `libwebp.a` +10988 B：llvm-ar 21 对 COFF 归档同时写 GNU 符号表与
  MSVC second linker member（旧产物只有一份）；解包后每个成员的 size 完全一致。
- `libmsgpackc.a` +12~16 B：源码树绝对路径变了，`__FILE__` 字符串长度不同。

二次执行 `compileAll` 全部 `UP-TO-DATE`；`stageAll` + `keelThirdpartyPublish` 产出 18 个 zip。

### 4.12 跨插件 Context 共享（2026-11-21）

`keel-plugin-hello` 新增两条路由：

- `GET /api/hello/context`：普通业务写法，直接 `ctx.components()`（本地组件表）；
- `GET /api/hello/context-bridge`：自检——`handleOf(ctx)` 模拟另一个插件拿到的 Context
  （`PublicApiObjects.handleOf` → `SharedExport.sharedRef`，等价于生成的代理编码共享参数），
  再用 `WebContextProxy` 经 Host 回环调用 `components()` / `webRequest()`。

```text
$env:KEEL_AUTH_WHITELIST_EXACT = "/api/hello/context,/api/hello/context-bridge"
gradlew -p keel-plugin-hello keelRun "-Pkeel.run.serveMs=30000" "-Pkeel.run.port=7193"
GET http://127.0.0.1:7193/api/hello/context
GET http://127.0.0.1:7193/api/hello/context-bridge
```

结果：

```text
/api/hello/context        → 200 {"message":"context","echo":"components=keel.web.request"}
/api/hello/context-bridge → 200 {"echo":"handle=3 components=keel.web.request path=/api/hello/context-bridge"}
```

Host 日志：

```text
registered keel.context handle=3 owner=1
registered moe.lolosia.keel.api.web.WebRequestComponent handle=4 owner=1
released handle=4 owner=1
released handle=3 owner=1
```

说明：Context 与挂载的 `WebRequestComponent` 都在 `handleOf(ctx)` 首次登记时登记，
请求结束由 `Context.destroy()` 按组件 → Context 的逆序释放；`@Permission` 未加，
但 Host 认证中间件默认要求登录，冒烟时用 `KEEL_AUTH_WHITELIST_EXACT` 把路径加入白名单。

### 4.15 ABI v2 与 MariaDB 真实后端（2026-11-21）

- `keel_database.h` 升到 `KEEL_DB_ABI_VERSION=2`；SQLite 与 MariaDB 驱动同步实现
  `last_insert_id` / `ping` 与新值类型；Host 严格校验 v2。
- MariaDB 用本机 Connector/C（3.3.8，服务器 10.11.6）编译，`.keel` 的
  `lib/mingwX64/` 同时带入口库与 `libmariadb.dll`，Host 整目录物化并用
  `LoadLibraryExW` + `LOAD_LIBRARY_SEARCH_DLL_LOAD_DIR` 加载。
- 冒烟（临时实例 `127.0.0.1:3307`，`KEEL_DB_URL=mysql://127.0.0.1:3307/keel_test`）：

```text

orm: insert=1/2, first=alice, page=[alice]/2, total=2, filtered=1, nullEmails=1, updatedNull=1, delete=1->1, rollback=1
```

- 同一份 hello 用 `sqlite://./check.db` 复跑，结果与 §4.14 一致；
  ORM 的方言来自能力包 `plugin.json` 的 `dialect`（hello 构建期是 sqlite，
  MariaDB 冒烟时 SQL 仍渲染成反引号 + `escape '\\'`，证明运行期方言生效）。
- MariaDB 侧覆盖：参数绑定（TEXT / DOUBLE / BOOL / BLOB）、`lastInsertId`、
  TEXT 与 BLOB 类型区分、事务回滚、ORM CRUD / 分页 / `LIKE` / NULL 更新。
