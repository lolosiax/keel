## 7. 易踩的坑

### 7.1 构建 / Gradle / 发布

- 单独构建 `keel-host` / `keel-plugin-hello` 时，除 `keel-logger-gradle-plugin`
  走 `pluginManagement.includeBuild` 外，编译器插件 jar 还要
  `--include-build=../keel-logger-compiler-plugin`，否则解析不到
  `moe.lolosia.keel.toolchain:keel-logger-compiler-plugin`。
- `keel-classpath-full` / `keel-api` 现在依赖 `keel-classpath`；单独 `-p` 构建必须带
  `--include-build=../keel-classpath`，否则去 Maven 找不到。
- `keel-plugin-hello` 自动依赖 `keel-classpath-full`；单独构建必须带
  `--include-build=../keel-classpath-full`。
- `keel-host` 的 `settings.gradle.kts` 通过 `pluginManagement.includeBuild` 引入
  `../keel-classpath-gradle-plugin`；`keel-plugin-hello` 引入 `../keel-plugin-gradle-plugin`。
  改插件后要重新构建插件，Gradle 会自动处理。
- 构建期工具各自带一份发布仓库配置；`local.properties` 始终按 `../local.properties` 找，
  单独 clone 某个构建时它必须与仓库根同级。
- `keel-launcher` 调用 `runHost(emptyArray())`，因为 Host `main` 现在带 `args`。
- Ktor 的 native 工件在 aliyun 镜像上会让 Gradle 按 `-mingwX64Main.klib` 这个名字找文件并失败；
  `keel-host/settings.gradle.kts` 必须把 `mavenCentral()` 放在镜像前面，否则 `--http` 构建不了。
- `keelPackage` 必须显式 `dependsOn(keelProcessManifest)`：仅靠
  `from(provider.flatMap { ... })` 不会建立任务依赖，打出的包会缺 `plugin.json`。
- 构建信息用 **git 提交时间**，不用构建时间：同源码在两台机器上编出的标识才一致。
- 改过 `keel-api` / `keel-abi` / `keel-host` 之后**必须先发布到 mavenLocal**，顺序
  `keel-classpath → keel-api → keel-abi → keel-host`（`publishHostExecutablePublicationToMavenLocal`），
  再跑 `keelPrepareRun --refresh-dependencies`；否则 IDEA 里的运行配置会用旧包，
  报 `Unresolved reference: CONSOLE_INPUT` / `'onMessage' overrides nothing` 这种「代码明明是对的」。

### 7.2 编译器插件 / KSP

- 编译器插件与 Kotlin 版本强绑定：`keel-logger-compiler-plugin` 的
  `compileOnly(kotlin-compiler-embeddable)` 必须与 `libs.versions.kotlin` 完全一致；
  升级 Kotlin 要同步升它并重跑 host / hello 的日志验证。
- IR 的 `arguments` 列表按“全部形参”排布（含 dispatch / extension receiver），
  写实参要按 offset 加 1；`IrGetEnumValueImpl` 是编译器 internal API，所以
  编译器插件调用 `Log.of` 的 `Int` 重载传 `kind.ordinal`。
- `-Xplugin` / `-P` 由 `KotlinCompilerPluginSupportPlugin` 自动挂载，不要手写
  `freeCompilerArgs`，否则插件 jar 不进 `@Classpath`、改了插件不重编。
- 实测改完编译器插件后，消费方 native 编译任务不一定重新执行；联调时先
  `gradlew -p <消费方> clean` 再编译，避免拿旧 IR 验证。
- KSP 处理器依赖必须在 `ksp<target>` 配置**创建的那一刻**加进去：KSP 在自己的
  `afterEvaluate` 里创建配置并固定处理器 classpath，晚于它的 `afterEvaluate` 再加就只有
  空 classpath（症状：`kspKotlinMingwX64` 跑完但什么都没生成，链接报
  `undefined symbol: keel_plugin_worker_main`）。所以 `moe.lolosia.keel.plugin` 用
  `configurations.configureEach` 挂 `keel-plugin-ksp`。
- KSP2 没有 KSP1 的回退：`ksp.useKSP2=false` 会直接报 "KSP1 is no longer available"。
- **IDEA 同步会编译中间源集的 metadata**（`compileNativeMainKotlinMetadata` 等），
  这些任务在 `-p <项目> linkDebug…` 里不会跑，所以本地能过、同步报错很常见：
  - `expect class` 继承接口时，必须在 expect 里显式声明 `override fun close()`
    （metadata 看不到各目标 actual）；actual 侧要写 `actual override fun close()`。
  - `nativeMain` 里直接用 `fseek` / `ftell` 会被 commonize 拒绝：mingw 的 `long` 是 32 位、
    linux 是 64 位，签名不一致。这类调用要拆成 `expect` / `actual`（见 `fileSizeOrNull`）。
  - 用到 keel-api 的 cinterop 声明的中间源集，需要在自己的 `gradle.properties` 里
    打开 `kotlin.mpp.enableCInteropCommonization=true`（根目录的不会下发）。

### 7.3 ABI / 线程 / 事件泵

- K/N 2.4 里 `kotlinx.cinterop.toWideString` 已不存在；要调 Windows 的 `W` API 得自己
  `allocArray<WCHARVar>` 拼 UTF-16。实测 mingw 的 `platform.posix` 有 `opendir` / `readdir`，
  但 `mkdir` 只有 path 一个参数（linux 是 path + mode），两端签名不同，必须 expect/actual。
- Kotlin 的 `@CName` 符号不会自动进 PE 导出表：不生成 `.def` 的话 dll 里只有 C 那些
  `__declspec(dllexport)` 符号，Host `dlsym(entry)` 直接拿到 null。
- 改了 `keel-abi/src/nativeCpp/*.c` 之后要确认 **归档任务重跑**：`keelAbiArchive<target>`
  以前没声明 inputs，只重编 `.o`、`.a` 还是旧的（症状：Kotlin 按新签名调用、C 还是旧签名，
  进程直接 access violation）。现在归档有 `inputs.dir`，链接任务也把库目录挂成输入。
- cinterop 对不完整结构体生成 `cnames.structs.*`，IDE 的 KMP 中间源集索引不到。
  `KeelQueueTag` 因此用 `KEEL_CINTEROP` 占位完整定义；改 ABI 头文件时别把宏分支删掉，
  除非 Kotlin 真的需要按值 / 按布局使用该类型。
- 新增事件 kind 要同时改三处：`keel_abi.h` 枚举、`PluginWorker.dispatch`、`HostPump.drain`。
  只改头文件的话，事件会在两端被静默丢掉，没有日志、没有报错。
- `HostPump` 的 pending 表只允许泵线程读写：外部线程只能通过 `HostPump.request`（Channel）提交，
  直接改表会有数据竞争。请求超时后迟到的 COMPLETE 会被丢弃并告警一次。
- `pushToPlugin` 的载荷由 Host 自己的 CRT 分配并挂 `keel_event_set_default_release`；
  队列拒收时必须就地 release，否则每失败一次漏一块内存。
- 同步等待循环里必须先认「自己的 correlation」，再交给 `HostPump.handleAsync`：
  反过来会把本次启动 / 控制台的 COMPLETE 当成其它请求的回包吞掉，表现为启动超时。
- `keel_plugin_shutdown` 之后的 `keel_plugin_bootstrap` 是二次进入同一 dll：C 侧会
  回收已退出的泵线程与 inbox、`memset` 重置状态并新建队列 / 泵线程；**泵线程仍存活时
  bootstrap 直接返回 `KEEL_ERR_INVALID`**，避免两个线程抢同一份 `g_plugin`。
  启动失败时 Host 会先 `request_shutdown` 并尽量 join，再让 entry 停在 disabled。
- **插件泵线程的空闲唤醒是个真坑**：`keel_plugin_set_wakeup()` 只写 `wake_at_ms`，
  不会打断已经阻塞的 `keel_queue_pop`；空闲时 `pump_timeout()` 返回 `KEEL_WAIT_FOREVER`，
  于是别的线程（管道读线程、任意后台线程）投进 `WorkerScheduler.pending` 的协程续体
  **永远不会执行**。表现：Host 一直在刷日志时插件正常，一旦安静下来，插件后台线程的一切都停摆。
  修法：`pump_main` 按 `PUMP_POLL_MS`(100ms) 分片等待并每次重算超时，只有真正到期才投 TIMER。

### 7.4 日志

- 插件日志走 Host 收件箱（256 条），日志风暴时会被丢弃；排查「日志缺行」先怀疑队列满。
- 自定义来源列必须同时给纯文本与 ANSI 版本：列宽按纯文本计算，否则 ANSI 转义会把对齐算坏。
- HTTP 日志的 TAG 是固定的 `HTTP IN` / `HTTP OUT`；状态码放在消息里，
  避免 TAG 随状态码变化而失去统一配色。
- 自定义来源列还要保留 `Printed at` 时，用 `Log.site()` 取调用点再传给 `emitSource`；
  不要把它藏进 `inline` 工具函数，否则记到的是 inline 体内的行号。
- keel-logger 的 IR 扩展只处理**当前编译模块**：依赖 klib 不会在消费端重打，
  inline 函数体由 klib 原样带入；库里的日志有没有站点取决于它自己编译时是否应用了插件。
- Ktor native 的 `KtorSimpleLogger` 直接 `println`，没有全局开关；要接管只能给
  `embeddedServer` 传自定义 `environment.log`（见 `KtorLogBridge`）。

### 7.5 HTTP / 路由

- 路由注册事件在**启动等待期**就会到达：`awaitComplete` / `requestPlugin` / `drain` 都必须调
  `HostPump.handleSnapshot`；漏一处会把注册当成「无关事件」丢掉，表现是 HTTP 404。
- Ktor catch-all 用 `route("{...}")`，必须写在 `/healthz` / `/ping` 之后，具体路由优先。
- 请求体只能在 Monitoring 阶段读一次：分发必须从 `call.attributes` 取，
  再调一次 `receiveText()` 会读不到内容。
- 从非泵线程向插件发请求前必须 `wakeHostPump()`，否则请求会卡在泵的 200ms `pop` 超时里。

### 7.6 控制台 / 窗口

- 控制台 / 信号处理函数里只能置 C 标志，不能调用 Kotlin；否则会跨运行时线程，行为不可预期。
- 自测 Ctrl+C 时注意：`CREATE_NEW_PROCESS_GROUP` 启动的进程默认屏蔽 `CTRL_C`，
  应发 `CTRL_BREAK` 到进程组，或直接在真实终端里按 Ctrl+C。
- stdin 读线程必须留在 C 侧（`keel_console.c`）：改成 Kotlin 里阻塞 `readLine` 会占住
  协程 Dispatcher 的线程；Windows 终端还要用 `ReadConsoleW`，`fgets` 会按 ANSI 码页出乱码。
- 控制台命令会同步等插件回包（3s 超时）；插件 `onCommand` 里做长耗时操作会卡住
  整个事件泵，包括 HTTP 请求与其它插件。
- `HostPlugins` 的启停 / 装卸只能在主线程（泵线程）调用；HTTP 线程直接调会与事件泵抢状态。
- `plugins remove` 之后重新 `install` 同一包会拿到**新的** `plugin_id`，路由按新 id 注册；
  旧 id 的映射故意保留，避免晚到的日志丢失插件名。
- conhost 的 cooked 模式在 Windows Terminal / ConPTY 下**不可信**：`ENABLE_PROCESSED_INPUT`
  设不上去（`SetConsoleMode` 返回成功但读回仍是关闭），退格被原样回显成 `^H` 并混进输入行，
  回车只回 `\r` 不换行。凡是自己开控制台读输入，都直接 `ReadConsoleInputW` 自己做行编辑。
- 遗留问题（未修）：开着控制台窗口停机时，Host 会打印
  `console 在 5000ms 内没有退出，跳过 join`（`g_pump_alive` 没在 5s 内清零，随后进程正常退出）。
  只在不曾开窗时干净，怀疑与会话相关线程的退出顺序有关。

### 7.7 运行期 / 插件 / 调度

- 插件库缓存每次启动都重写；dll 被占用时退到 `name.1.dll` / `name.2.dll`。
  联调 ABI 一般不用清缓存，但缓存目录里会留下旧编号文件。
- `plugin.json` 的 version 是 `0.1.0`，包名是 `0.1.0-SNAPSHOT`，暂未统一。
- Host 默认会打印 `embedded host.txt`，这是临时验证输出，后续启动器接入时会替换。
- `FileZipClasspath` 的条目读取每次打开文件；语义正确，但高频读取可以后续做句柄复用。
- 不要把 `plugin_id` 当稳定身份缓存或写盘：它每次启动按加载顺序重新分配（§3.8），
  持久化标识一律用 manifest 的 `id`。
- 插件侧 `PluginContext.metadata` 只有 `id` 有值；展示名由 Host 侧的 `PluginNames` 提供，
  别在插件里用 `metadata.name` 拼模块名（会是空串）。
- `PluginContextImpl` 的 `callbacks` 与 `KeelServer` 的 `events` / `services` / `messenger` /
  `plugins` 仍是 `error(...)`：在 `onLoad` / `onEnable` 里访问会抛异常，
  `bootstrap` 返回 `KEEL_ERR_FAILED`，外部表现是「插件启动失败」而不是「功能尚未实现」。
- 默认常驻只能靠杀进程结束：不会执行插件 `onDisable`，也不会 drain 最后的日志；
  冒烟用 `--once`，定时演示用 `--serve-ms=<n>`，两者都会走优雅 shutdown。
- `Scheduler.schedule` / `TaskHandle.cancel` 只能在 Worker 线程调用；任务表无锁，
  从别的线程调用会与 `tick` 竞争，`keel_plugin_set_wakeup` 也假定单写者。
- 周期任务里做长耗时同步操作会占住 Worker 线程：事件分发、其它任务、PING 回包都会排队，
  长任务应拆成多次短任务或交给协程（`ctx.scope`，M1-5）。
- Windows 上刚写出的 dll 立刻 `LoadLibrary` 可能被 Defender 扫描阻塞数秒（安装时观察到 ~3s），
  这是环境行为，不是事件泵卡住。
- 后台流（`Log.observe` 之类）在插件停用时必须自己收尾：`callHost` 会抛
  `HostRequestException("插件已停用…")`，没人接就是 `Uncaught Kotlin exception` + 进程退出。
- `callHost` 也得分片等待（100ms 一片）并在每片检查 `PluginWorker.plugin == null`，
  否则停用时会把整个超时（3s）等满才返回，拖慢 `onDisable`。
