# Kotlin/Native 插件化 Host + Modules 架构 — 技术探讨文档

> 用途：交由负责 Kotlin/Native 实现的工程师/智能体评估可行性、验证风险、细化方案。
> 本文档汇总了前期讨论中已确认的约束、候选架构、关键设计模式与待验证问题，不预设最终结论。

---

## 1. 背景与目标

### 1.1 业务目标
构建一个 **Host + Modules** 的插件化服务框架，模块以动态库（`.so` / `.dll` / `.dylib`）形式交付，支持：

- 启动 → 加载 → 运行 → 卸载 → 删除 的全生命周期
- 模块可独立升级、原位替换，不要求重启 Host 进程
- 部署目标包含边缘设备（代表型号：**RK3566**，4× Cortex-A55 @ 1.8GHz，Geekbench 5 单核约 416）

### 1.2 设计意图的类比
期望的系统形态**类似于 Tomcat / Servlet / WAR 部署模型**：

- Host 是容器，负责生命周期、路由、上下文注入
- Module 是部署单元，提供业务逻辑
- 模块之间可协作，共享账户系统、RBAC、请求上下文

### 1.3 与 Tomcat/WAR 的关键差异（必须在设计时正视）

| 维度 | Tomcat (JVM) | 本方案 (Kotlin/Native) |
| :--- | :--- | :--- |
| 运行时 | 全进程共享一个 JVM | **每个动态库静态链接一份独立 Kotlin/Native 运行时** |
| 类加载隔离 | ClassLoader 层次结构 | 无类加载器概念，C ABI 是唯一边界 |
| 卸载 | 可卸载 ClassLoader（虽易泄漏） | **运行时不支持安全卸载** |
| 对象传递 | 跨模块直接传引用 | 只能传 blittable 类型 / 不透明指针 |
| 热部署 | 有成熟实践（但有类加载器泄漏） | 无成熟先例，需自定义协议 |

**结论：可以借鉴 Tomcat 的架构思想（容器/部署单元/生命周期），但不能假设 JVM 的隔离与卸载语义在 Kotlin/Native 上成立。**

## 2. 已确认的硬约束

以下约束来自 Kotlin/Native 运行时设计与社区实践，**不是可以通过工程手段绕过的**：

### 2.1 运行时不可安全卸载
- Kotlin/Native 运行时静态链接进每个动态库，模块被 `dlopen` 后形成**独立的 Kotlin 实例**。
- `dlclose` 对 Kotlin/Native 模块**不安全**：TLS 析构器、GC 工作线程、内部线程状态会在库解除映射后触发延迟崩溃（有报告约 18 秒后 SIGSEGV）。
- 安全语义只能是"递减引用计数，**永不 unmap**"。
- **推论：同进程内，模块映像随每次"升级加载"单调累积，直至进程退出。**

### 2.2 跨运行时对象传递不安全
- Host 与 Module 不共享堆、对象头、类型系统。
- 直接传递 Kotlin 对象/接口会导致 `ClassCastException` 或段错误。
- `StableRef` 可将 Kotlin 对象钉住并暴露为 `COpaquePointer`，但**必须手动 `dispose()`**，否则永久泄漏。

### 2.3 C ABI 的类型约束
- 只能传递 **blittable** 类型：标量、C 结构体（`CValue`/`CValuesRef`）、C 字符串、原始指针。
- `CValue` 在 Kotlin 堆创建，使用时临时复制到 C 堆，**每次字段访问可能触发复制**，高频场景有性能代价。
- 复杂数据推荐"**C ABI + 紧凑二进制序列化**"（Protobuf/CBOR），避免 JSON（RK3566 上开销被放大）。

### 2.4 协程不能直接跨 C ABI
- `suspend fun` 编译为 CPS，携带 `Continuation<T>`，C 中无对应类型，**无法用 `@CName` 导出**。
- 异步跨边界必须退化为 **C 回调 + 用户数据指针**。
- Kotlin/Native 协程**线程绑定**，活跃 continuation 不能迁移线程。
- 调度器实例**不能跨运行时共享**：调度器锚定线程与运行时内部状态，跨运行时注入会导致 TLS/GC 根冲突。
- 取消语义**不会自动跨 C ABI 传播**，需显式建模。

### 2.5 Windows 文件锁
- 正在被加载的 DLL 不能被覆盖或删除，但**可以在同卷内重命名**。
- 可行模式：`MoveFileEx` 重命名为 `.old` → 放置新文件 → `MOVEFILE_DELAY_UNTIL_REBOOT` 安排旧文件删除。
- 该模式是 Chrome / Squirrel 等自动更新框架的基础。

## 3. 候选架构

### 3.1 架构 A：进程隔离 + RPC
- Host 与每个 Module 为独立进程，通过 UDS / gRPC 通信。
- **优点**：唯一能实现物理卸载（进程退出即回收全部内存与文件锁）。
- **缺点**：上下文需序列化传递；链式调用有累积延迟；Host 需承担服务发现/代理职责，有退化为 Nginx 式单向代理的风险；模块间同步调用需代理插件模式支撑。
- **RK3566 性能估算**：Protobuf + UDS 单次 RPC 约 20–60 µs；3 跳串行约 90–180 µs。若业务耗时 > 5ms，占比可接受；链路过长或业务极轻则成为瓶颈。

### 3.2 架构 B：同进程 C ABI + 每模块 Worker 线程 + 队列
- Host 与所有 Module 同进程，通过 C ABI 通信。
- 每个 Module 拥有**专属 Worker 线程**（非 Host 运行时初始化）与**事件队列**。
- 模块间通过投递消息到对方队列通信；完成通知通过 C 回调**唤醒**原始模块的 Worker（不直接在其上执行）。
- **优点**：模块可共享 Host 的活上下文（经不透明句柄）；无跨进程序列化开销；线程归属清晰。
- **缺点**：**无法物理卸载**（运行时不可卸载）；模块映像随升级累积；需手动管理 `StableRef` 引用计数、取消传播、跨模块序列化协议。

### 3.3 架构 C：混合
- 对**需独立热更新**的模块用进程隔离；对**高频交互、无需独立卸载**的模块合并进 Host 进程。
- 代价是两套通信机制并存，工程复杂度上升。

**当前讨论聚焦于架构 B**，因为它最接近 Tomcat/WAR 的"同容器内协作"心智模型，且满足 RK3566 的性能预期。但需明确接受"物理卸载不可行，依赖 systemd 定时重启兜底"。

## 4. 架构 B 的关键设计

### 4.1 不透明句柄（HWND 模式）

- Host 将请求上下文（含账户、RBAC、Bundle 等）封装为 Kotlin 对象，用 `StableRef.create()` 钉住，生成 `COpaquePointer` 句柄。
- 模块**永远不直接解引用句柄**，所有访问通过 Host 导出的 C ABI 函数。
- **必须实现引用计数协议**：每个句柄副本的使用方负责 `ctx_release(handle)`；Host 在计数归零时 `dispose()`。
- **Ktor `ApplicationCall` 不可放入长期句柄**：它是协程作用域绑定的。应在 Host 进入模块调用前，把 `call` 中模块所需信息（principal、路由参数、追踪 ID）**提取到 `RequestContext` 对象**，只传递该对象的句柄。

### 4.2 每模块 Worker 线程

- Worker 线程必须由 **C/POSIX 线程**创建（`pthread_create` 或 C interop），**不能**经 Host 的 Kotlin/Native 调度器创建，避免 TLS 污染。
- Worker 循环（伪代码）：

```
while (running) {
    event = queue.pop()          // 阻塞等待
    switch (event.type) {
        TASK:     module_dispatch(event.payload)
        COMPLETE: resume_local_coroutine(event.payload)
        CANCEL:   mark_cancelled(event.taskId)
    }
}
```

- 每个 Worker 线程只被**一个** Kotlin/Native 运行时初始化，TLS、GC 注册、线程清理归属清晰。

### 4.3 协程边界：`cancelableCoroutine`

Host 的 Ktor 路由侧：

```kotlin
suspend fun handle(call: ApplicationCall) {
    val ctx = RequestContext.from(call)          // 提取所需信息
    val handle = StableRef.create(ctx).asCPointer()
    val result = cancelableCoroutine<String> { cont ->
        // 投递任务到模块 Worker 队列（通过 C ABI）
        module_post_task(moduleQueue, handle, completionCallback)
        cont.invokeOnCancellation {
            module_cancel(moduleQueue, taskId)    // 显式传播取消
        }
    }
    call.respond(result)
}
```

- `completionCallback` 是 `staticCFunction`（非捕获），由模块 Worker 在**自己的线程**上调用，仅负责把 resume 动作投递回 Host 调度器，**不直接在回调中 resume**。
- 取消需通过 `invokeOnCancellation` 显式通知模块。

### 4.4 跨模块协作：队列 + 回调

- 模块 A 需要 B 处理时，向 B 的队列投递消息（携带 `StableRef` 句柄与完成回调）。
- B 在自己的 Worker 上处理，完成后向 A 的队列投递 COMPLETE 消息，**唤醒** A 的 Worker。
- **执行权不跨线程**：A 的 continuation 始终在 A 的 Worker 上恢复。
- 回调函数指针必须非捕获；所需上下文通过独立的 `COpaquePointer`（`StableRef`）传入。

### 4.5 跨模块对象图序列化：两阶段批量快照协议

**问题**：对象图含来自 5 个模块的委托对象且互相引用，通用序列化器自动遍历会引发"模块传递风暴"。

**前提澄清**：
- 若委托对象只是视图、数据在 Host 底层对象上 → **序列化器绕过委托，直接序列化 Host 对象**，跨模块往返为 0。Host 需维护"委托句柄 → 底层对象"映射表。
- 若委托对象持有模块本地状态 → 采用下述批量协议。

**两阶段协议**：

1. **Host 侧图遍历（阶段一）**：序列化器遍历对象图，遇到跨模块对象时不立即调用，而是按模块分组记录句柄，维护"已访问集合"防循环。遍历结束后得到"模块 → 待序列化句柄列表"。
2. **按模块批量请求（阶段二）**：Host 向每个涉及模块发送**一次** `serialize_batch(handles[], outBuffers[])`。模块返回"字段值 + 对其他模块对象的引用 ID"（**不递归拉取**）。
3. **Host 合并（阶段三）**：Host 在本地将扁平数据与引用 ID 组装为完整输出；循环引用通过 ID 解决。

**往返次数 = 涉及的模块数（上例 5 次），与引用边数无关。**

**关于"不能维护副本"**：序列化天然产生时间点快照；实时一致性应通过共享 Host 句柄保证，而非通过序列化。两者不矛盾，但需在业务层明确语义。

## 5. 文件替换与生命周期兜底

### 5.1 重命名-替换（同进程方案下）
1. `MoveFileEx` 将 `module.dll` 重命名为 `module.dll.old`（同卷）。
2. 放置新版本到原路径。
3. 旧文件用 `MOVEFILE_DELAY_UNTIL_REBOOT` 安排重启后删除（通常需管理员权限）。

### 5.2 systemd timer 定时重启
- 配置 `OnCalendar=*-*-* 04:00:00` 调用 `systemctl restart <service>`，在低峰期强制回收进程地址空间（含所有历史模块映像）。
- 服务单元配置 `Restart=always` 作为自愈。
- **这是架构 B 下解决"映像累积"与"文件锁"的最终手段**，不可省略。
- 社区案例：cron → systemd timer 后因内存泄漏导致的中断减少 78%。

### 5.3 监控指标
- 监控 **Private Commit**（而非仅 Working Set），准确跟踪映像累积速度，为是否切换架构 A 提供数据。

## 6. 已识别的风险清单

| 风险 | 影响 | 缓解 |
| :--- | :--- | :--- |
| 多运行时共享单 Worker 线程的 TLS/GC 冲突 | 崩溃/内存损坏 | 已改为每模块专属 Worker，需原型验证 |
| `StableRef` 未 dispose | 堆永久泄漏 | 引用计数协议 + 代码审查 + 泄漏检测 |
| 序列化风暴 | 延迟爆炸 | 两阶段批量快照协议；优先 Host 直接序列化 |
| 取消未跨边界传播 | 后台空转、资源泄漏 | `invokeOnCancellation` 显式调用 cancel C ABI |
| 回调在错误线程执行 | 跨运行时崩溃 | 回调只做通知，执行权留在各自 Worker |
| JSON 用于热路径 | RK3566 上开销不可接受 | 强制 Protobuf/CBOR |
| 模块映像累积 | 内存单调增长 | systemd 定时重启；监控 Private Commit |
| `CValue` 隐式复制 | 高频访问性能下降 | 粗粒度 API，避免逐字段 `CValue` 访问 |

## 7. 待验证的原型问题（建议按序执行）

1. **双模块 Worker 原型**：两个最小 Kotlin/Native 模块，各自 Worker 线程 + 队列，高频互投 `StableRef` 句柄并在回调中 dispose，持续运行数小时，观察 GC、内存、线程稳定性。**这是架构 B 成立的前提。**
2. **C ABI + Protobuf ping-pong 基准**：在 RK3566 实机上用典型 `RequestContext` 消息测量单次往返延迟，校准 3 跳链路的真实边界开销。
3. **`StableRef` 生命周期验证**：模拟异常路径（模块处理中抛异常、Host 取消、队列满），验证引用计数在各种路径下归零。
4. **序列化协议验证**：构造含 5 模块互引的对象图，测量两阶段协议的往返次数与端到端延迟，确认与引用边数无关。
5. **文件替换验证**：在 Windows 上验证"重命名-替换-重启删除"完整流程；在 Linux 上验证 systemd timer 重启后新模块被正确加载。
6. **取消传播验证**：客户端断开连接后，确认模块侧任务被终止且相关 `StableRef` 被释放。

## 8. 性能预算参考（RK3566）

| 操作 | 估算（需实测校准） |
| :--- | :--- |
| Protobuf 编解码（小消息） | 5–20 µs |
| UDS 往返 | 10–30 µs |
| 单次模块间 RPC（Protobuf + UDS） | 20–60 µs |
| 3 跳串行 RPC | 90–180 µs |
| 同进程 C ABI 函数调用 | 亚微秒级 |
| futex 线程唤醒 | 微秒级 |
| JSON 往返（热路径） | 数百 µs，**不推荐** |

**判断依据**：若业务逻辑总耗时 > 5ms，90–180 µs 的边界开销占比 < 4%，可接受；若业务极轻（< 1ms）且链路 > 5 跳，需重新评估。

## 9. 开放问题（供实现者讨论决策）

1. 架构 B 的双模块 Worker 原型是否能在目标 Kotlin/Native 版本上稳定运行？若失败，是否切换到架构 A 或 C？
2. `StableRef` 引用计数协议由 Host 集中管理，还是分散到各模块？分散时如何防止模块"忘记 release"？
3. 模块间同步调用是否允许？若允许，其实现是否仍是"投递 + 等待 COMPLETE 消息"，从而不违反"执行权不跨线程"原则？
4. 序列化协议是否统一为 Protobuf，还是允许模块声明自定义格式？跨模块引用 ID 的命名空间如何分配？
5. Ktor `ApplicationCall` 中哪些字段必须进入 `RequestContext`，哪些可由模块通过句柄按需查询？需列出字段清单。
6. Windows 与 Linux 的文件替换策略是否统一为"重命名 + 重启删除"，还是 Linux 上可利用 `unlink` 已打开文件的语义简化流程？
7. systemd 重启窗口内，是否有正在执行的长任务需要优雅排水（drain）？排水超时如何配置？
8. 是否需要在 Host 侧引入"模块健康检查"与"Worker 队列积压告警"，作为映像累积/泄漏的早期信号？

## 10. 建议的实现路径

1. **阶段一（可行性）**：完成第 7 节原型 1–3，确认架构 B 的运行时安全性。
2. **阶段二（协议）**：定义 C ABI 函数表（句柄操作、队列投递、取消、序列化批量接口），完成原型 4–6。
3. **阶段三（框架）**：实现 Host 容器（模块发现、加载、生命周期、Ktor 集成、`RequestContext` 注入）、模块 SDK（Worker 循环、队列封装、协程桥接）。
4. **阶段四（运维）**：接入 systemd timer、文件替换脚本、监控（Private Commit、队列深度、GC 指标）。
5. **持续评估**：若映像累积速度或 RPC/队列延迟超出预算，评估切换到架构 C（热更新模块进程隔离）。
